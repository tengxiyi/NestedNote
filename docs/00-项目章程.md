## 1. 项目名称

### 1.0 品牌名与工程标识（重要区分）

> **对外用品牌名，对内用工程标识。两者刻意不同，且都必须严格遵守。**

| 用途 | 用哪个 | 示例 |
|---|---|---|
| 品牌、UI 显示、安装包、商店、官网、文档标题 | **拾光笔记 / NestedNote** | `NestedNote-1.0.0-windows-x64.msi` |
| 仓库、crate、包名、数据库、数据目录、环境变量、日志字段、FFI 符号 | **`nested`（工程标识）** | `nested-core`、`package:nested`、`NESTED_HOME` |

**理由**：品牌名可能因商标/市场原因调整，而工程标识一旦落地改起来代价极高（crate 名、包名、磁盘目录、用户数据路径、协议字段都牵连）。因此工程层统一使用中性短标识 `nested`，品牌层使用 `拾光笔记 / NestedNote`，两者通过 `nested_core::branding` 单点映射。

### 1.1 品牌名

| 项 | 值 |
|---|---|
| 中文名 | **拾光笔记** |
| 英文名 | **NestedNote** |
| 一句话定位 | 拾起每一段时光，层层收好——笔记先安家在你的硬盘上，再谈云端 |
| 名称由来 | **拾光**＝拾取散落的时光碎片（"拾"兼谐音"十"，暗含一层层累积）；**Nested**＝层层嵌套（笔记本树 / 块树 / 同步层级），**Note**＝它终究是一本笔记。中文取"记"，英文取"叠"，同一内核的两面 |
| 命名路数 | 与"印象笔记"同脉：抽象意象词 + 笔记，靠画面感动人，不靠功能名词自述 |
| 应用显示名 | 拾光笔记（zh-CN）｜ NestedNote（其他语言） |
| 品牌英文单字 | `拾光` |

### 1.2 工程标识

| 项 | 值 |
|---|---|
| 命名空间（Cargo） | `nested` / `nested-*` |
| 命名空间（Dart） | `nested` |
| 反域名 | `app.nestednote` |
| 数据库与环境标识 | `nested`（如 `nested.db`、`NESTED_HOME`） |
| 简称（口语/commit 前缀） | `nest` |
| 仓库名 | `nested` |

### 1.3 名称的取舍记录

| 备选 | 评价 | 是否采用 |
|---|---|---|
| Obsidian / Notion 类既有名 | 已被占用，商标冲突 | ✗ |
| Slate | 撞 Rust GUI 框架 `slate`，也撞已停产笔记应用 | ✗ |
| Corvid（鸦科，善缓存与记忆） | 有趣但英文释义冷门，中文难读 | ✗ |
| Lumen | 撞大量同名项目 | ✗ |
| 巢记 / Nested | 中文"巢"偏动物化、"记"偏工具说明，品牌感不足 | ✗ |
| 叠叶 / 垒页 / 沓 / 琅嬛 | 意象准确但大众好感度与记忆点不足（详见讨论记录） | ✗（备选库） |
| **拾光笔记 / NestedNote** | 中文温暖、有画面、好记（对标"印象笔记"路数）；英文点明"嵌套 + 笔记"的产品本质；中英互为表里 | **✓ 定稿** |

> 若将来必须改名（商标冲突等），因为存在 §1.0 的分离设计，通常**只需改品牌层**：`nested_core::branding` 常量、应用显示名、安装包名、商店文案。
> 数据目录、crate 名、数据库名等工程标识可保持不变。
> 因此**禁止**在业务代码里硬编码品牌名字符串，统一从 `nested_core::branding` 与应用配置读取。

### 1.4 命名规范速查

```text
品牌显示名:  拾光笔记（zh-CN）｜ NestedNote（en 及其他）
仓库:    nested/
目录:    apps/flutter, crates/nested-core, server/, docs/, scripts/
Rust crate:  nested-core, nested-model, nested-db, nested-search,
             nested-attachment, nested-import, nested-export,
             nested-sync, nested-crypto
Rust 模块:  snake_case
FFI 前缀:   nested_*          （生成的绑定函数与符号统一前缀）
Flutter 包: package:nested/...
数据库:     nested.db（本地） ｜ nested_server（服务端 PostgreSQL）
文件目录:   ~/<AppData>/NestedNote/{nested.db, attachments/, cache/, logs/}
环境变量:   NESTED_HOME, NESTED_LOG, NESTED_SERVER_URL, NESTED_DEVICE_ID
日志字段:   app="nested"
发布产物:   NestedNote-1.0.0-windows-x64.msi / .dmg / .apk / .ipa
```

> 注意：**数据目录用 `NestedNote`（品牌）**，因为它对用户可见、可能被手动备份；
> **数据库文件名与环境变量用 `nested`（工程标识）**，因为它们是纯内部约定。
> 这条差异是有意为之，不要"顺手统一"。

## 2. 项目愿景与目标

### 2.1 愿景

> **数据先落在你自己的设备上，且永不丢失；界面只是数据的投影。**

做一款 Windows / macOS / iOS / Android 四端体验一致、低内存、可离线、可自托管、可长期演进的现代笔记应用。第一阶段的成功标准不是"像 Evernote 的界面"，而是**一个稳定、可测试、可演进的数据内核**。

### 2.2 第一阶段（v1.0）目标

- 笔记本 / 笔记 / 标签三级组织；块结构化富文本；图片与任意文件附件
- SQLite + FTS5 全文搜索，10 万笔记搜索 < 300 ms
- 本地优先：任何操作先落本地、立即更新 UI、后台再说同步
- 自动保存、崩溃不丢数据、软删除 + 回收站 + 可恢复备份
- Markdown / HTML / TXT / ENEX 导入，Markdown / HTML / JSON 导出
- 完整数据备份与恢复（manifest + 内容 + 附件）
- 四个平台均可构建、可运行、可打包

### 2.3 非目标（明确不做）

- 实时多人协同编辑（P7 之后才评估）
- Evernote UI 1:1 克隆、自研排版引擎、自研同步协议、自研数据库
- 插件系统、企业权限、团队协作
- 第一版引入向量数据库 / CRDT / 云端强依赖

### 2.4 北极星指标（North Star）

| 类别 | 指标 | 目标 | 验证方式 |
|---|---|---:|---|
| 数据 | 已提交的笔记数据丢失 | **0** | 崩溃注入测试 + 备份恢复演练 |
| 性能 | 冷启动 | < 1.5 s | `bench` 套件 |
| 性能 | 常驻启动 | < 1 s | 同上 |
| 性能 | 空闲内存（Windows） | 50–100 MB | 同上 |
| 性能 | 编辑态内存 | 100–200 MB | 同上 |
| 性能 | 移动端内存 | < 100 MB | 同上 |
| 性能 | 10 万笔记搜索 | < 300 ms | 同上 |
| 性能 | 本地打开笔记 | < 100 ms | 同上 |
| 性能 | 单条 SQL 查询 | < 20 ms | 同上 |
| 性能 | UI 帧率 | 60 FPS（P95 帧时间 < 16.7 ms） | Profile 模式实测 |
| 质量 | `nested-core` / `nested-db` 行覆盖率 | ≥ 80% | CI |
| 质量 | 导入导出格式往返（round-trip）测试 | 100% 通过 | CI |
| 一致性 | 四端同一数据集的渲染差异 | 无阻塞级差异 | 跨端截图/结构化对比 |

**约束**：这些是工程目标，不允许为凑数字牺牲数据安全与稳定性（见《铁律》T1）。

## 4. 技术基线（锁定）

| 层 | 选型 | 锁版本策略 |
|---|---|---|
| UI | Flutter / Dart（stable channel） | `pubspec.lock` 提交入库 |
| Core | Rust（stable，MSRV 随 `rust-toolchain.toml`） | `Cargo.lock` 提交入库 |
| FFI | flutter_rust_bridge v2 | 锁定 minor，升级需 ADR |
| 本地库 | SQLite（bundled）+ FTS5 | 由 `rusqlite` bundled feature 固定 |
| 服务端 | Rust + Axum + Tokio + SQLx | `Cargo.lock` |
| 服务端库 | PostgreSQL | 迁移脚本入库 |
| 对象存储 | S3 兼容（开发期用 MinIO） | docker-compose 固定镜像 tag |
| 状态管理 | Riverpod | — |
| 日志 | Rust `tracing` ｜ Dart `logging` | — |
| 错误 | Rust `thiserror` + `anyhow`（边界） | — |

> 任何基线变更（换 ORM、换编辑器库、换状态管理）必须先有 ADR，再动代码。见《[02-工程铁律.md](02-工程铁律.md)》A8/A9 与 M2。

## 6. 治理与角色

- **产品/技术负责人（1 人）**：决定范围、批准 ADR、批准阶段晋级（Gate）。
- **核心开发者（1–3 人）**：Rust Core / Flutter / Server 分工，但**不允许长期只由一人理解某一模块**（须有 Design Doc + 测试）。
- **决策机制**：
  - 影响架构、数据格式、协议 → 必须 ADR（`docs/adr/NNNN-*.md`）
  - 影响 UI 细节 → PR 描述即可
  - 影响范围（新增/删除功能） → 更新《开发计划》并记入变更日志

### 6.1 ADR 目录约定

```text
docs/adr/
├── 0001-record-architecture-decisions.md   （元 ADR：本仓库使用 ADR）
├── 0002-block-model-over-html.md
├── 0003-content-addressable-attachments.md
├── 0004-revision-log-before-crdt.md
└── ...
```

ADR 模板：

```markdown
# ADR NNNN：<决策标题>
- 状态：提议 / 已接受 / 已废弃 / 被 NNNN 取代
- 日期：YYYY-MM-DD
- 背景：我们面对什么问题？
- 决策：我们决定做什么？
- 备选方案：还考虑过什么，为何不选？
- 后果：变好了什么 / 变坏了什么 / 后续要做什么？
```
