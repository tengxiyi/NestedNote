## 0. 计划总览

| 阶段 | 目标 | 预估 | Gate 产物 |
|---|---|---:|---|
| **P0 工程基座** | 双工具链可构建、CI 可跑 | 1–2 周 | 四目录骨架 + `cargo test`/`flutter test` 全绿 |
| **P1 Rust Core** | 数据内核（模型/DB/搜索/附件/导入导出） | 4–6 周 | 无 UI 可用的 CLI + 基准报告 |
| **P2 Flutter MVP** | 桌面最小可用（列表 + 编辑 + 自动保存） | 3–4 周 | 重启不丢数据 |
| **P3 桌面完整版** | 三栏 UI + 富文本 + 标签/回收站/导入导出 | 5–8 周 | 第一阶段验收 14 条全通过 |
| **P4 压力与优化** | 10 万笔记 / GB 级附件预算达标 | 4 周 | 性能与内存报告 |
| **P5 移动端** | Android / iOS 完整可用 | 5–8 周 | 移动端验收清单 |
| **P6 云同步** | 账号/设备/Revision/附件同步/冲突 | 6–10 周 | 双设备同步演练 |
| **P7 高级（可选持续）** | OCR / 版本历史 / AI / 语义 / WebDAV / CRDT | 持续 | 各特性单独 Gate |

**总工期估算（1–2 人全职）**：约 **7–9 个月** 到 P6 完成；单人兼职开发按 ×1.8–2.5 折算。
**里程碑不可压缩项**：P1 与 P3，压缩它们只会把成本转移到后期数据迁移与线上事故上。

## 2. P1 Rust Core（4–6 周）

> 本阶段**不写 Flutter 业务 UI**，只写 Rust 与一个用于验收的 CLI（`nested-cli`）。

### 2.1 任务分解

#### 2.1.1 数据模型（`nested-model`）

| ID | 任务 | 说明 |
|---|---|---|
| P1-1 | 领域类型定义 | `Notebook` / `Note` / `Tag` / `Attachment` / `Revision`，ID 统一 UUIDv7（时间有序） |
| P1-2 | Document Model 定义 | `Document { version, metadata, blocks[] }`，Block 枚举 13 种（§6 of 技术文档） |
| P1-3 | 序列化契约 | serde 命名与字段稳定性；**新增字段必须可选、不删不改语义** |
| P1-4 | 校验规则 | 标题长度、块嵌套深度、单文档块数上限、非法 MIME 拒绝 |

#### 2.1.2 存储层（`nested-db`）

| ID | 任务 | 说明 |
|---|---|---|
| P1-5 | SQLite 打开与 PRAGMA | `journal_mode=WAL`、`foreign_keys=ON`、`busy_timeout`、`synchronous=NORMAL` |
| P1-6 | Migration 框架 | `migrations/0001_init.sql` …；启动时 `user_version` 检查 → 迁移 → 校验 |
| P1-7 | 核心表 | `notebooks` `notes` `tags` `note_tags` `attachments` `note_attachments` `documents` `revisions` `sync_operations` `settings` |
| P1-8 | 索引设计 | `notes(updated_at DESC)`、`notes(notebook_id, is_deleted)`、`note_tags(tag_id)` 等；附 `EXPLAIN QUERY PLAN` 验证 |
| P1-9 | Repository 层 | 全部 CRUD 走参数化查询；**禁止字符串拼 SQL** |
| P1-10 | 事务边界 | 单次业务操作 = 单事务；跨表写（笔记 + 文档 + 标签 + revision）原子提交 |
| P1-11 | 软删除与回收站 | `is_deleted` / `deleted_at`；恢复与 GC（保留期默认 30 天，可配置） |

#### 2.1.3 搜索（`nested-search`）

| ID | 任务 | 说明 |
|---|---|---|
| P1-12 | FTS5 外部内容表 | `notes_fts(title, content, tags)` + 触发器或应用层同步 |
| P1-13 | 中文分词策略 | FTS5 默认分词对中文不友好 → 采用 `unicode61` + 二进制/双字切分方案；**必须有对比基准**（ADR 记录） |
| P1-14 | 查询语法 | 关键词、短语、前缀、`tag:`、`notebook:`、时间过滤；结果高亮片段 |
| P1-15 | 增量索引 | 保存笔记时增量更新；重建索引命令 `nested-cli reindex` |

#### 2.1.4 附件（`nested-attachment`）

| ID | 任务 | 说明 |
|---|---|---|
| P1-16 | CAS 存储 | `SHA-256` → `attachments/ab/cd/<hash>`；流式计算，不整文件入内存 |
| P1-17 | 引用计数与 GC | 无引用附件延迟回收；回收需在同步完成后（P6 前置约束） |
| P1-18 | 缩略图管线 | 图片生成 ≤ 512 px 缩略图，缓存于 `cache/thumbs/`，可失效重建 |
| P1-19 | 原子写 | 临时文件 + rename；断电不产生半截文件 |

#### 2.1.5 导入导出与备份（`nested-import` / `nested-export`）

| ID | 任务 | 说明 |
|---|---|---|
| P1-20 | Markdown 导入/导出 | 块模型 ↔ Markdown 双向；**round-trip 测试** |
| P1-21 | HTML 导入/导出 | 清洗脚本、白名单标签 |
| P1-22 | TXT 导入 | 分块策略、编码识别（UTF-8/GBK） |
| P1-23 | ENEX 导入 | Evernote 导出解析（流式 XML），附件抽取入 CAS |
| P1-24 | JSON 导出 | 完整块模型导出，作为长期归档格式 |
| P1-25 | 备份 / 恢复 | `backup/{manifest.json, notes/, attachments/, metadata/}`；恢复为**全量替换或新建库**，不合并 |
| P1-26 | 备份完整性校验 | manifest 含每文件 SHA-256 与计数；恢复前校验 |

#### 2.1.6 内核服务与错误（`nested-core`）

| ID | 任务 | 说明 |
|---|---|---|
| P1-27 | 业务 API（业务语义，非 SQL 语义） | `create_note` `update_note` `get_note` `search_notes` `list_notebooks` … |
| P1-28 | 结构化错误 | `DatabaseError` `NetworkError` `ValidationError` `SyncConflict` `PermissionError` `AttachmentError` `ImportError` |
| P1-29 | 日志与脱敏 | tracing 分级；正文/密码/token/密钥不进日志 |
| P1-30 | 加密（`nested-crypto`） | DB 加密（SQLCipher 或字段级，ADR 决定）+ 密钥存平台 Keychain/Keystore |
| P1-31 | 大文档策略 | 块级懒加载接口：先取块元数据，再按需取块内容 |

#### 2.1.7 测试与基准

| ID | 任务 | 说明 |
|---|---|---|
| P1-32 | 单元 + 集成测试 | 每个 Repository 方法至少 1 正常 + 1 边界 + 1 失败路径 |
| P1-33 | 数据生成器 | `nested-cli gen --notes 100000 --attachments 1GB` |
| P1-34 | 基准套件 | criterion：插入、查询、搜索、导入、哈希、缩略图 |
| P1-35 | 崩溃注入测试 | 写入过程中 kill 进程，重启后库可打开且已提交数据完好 |
| P1-36 | 迁移测试 | 每个历史迁移都在 CI 中从旧库升到最新并跑一致性查询 |

### 2.2 DoD

- [ ] `nested-cli` 可 `gen / search / import / export / backup / restore / reindex / bench`
- [ ] 核心 crate 行覆盖率 ≥ 80%（CI 报告）
- [ ] 10 万笔记库：搜索 P95 < 300 ms；单条查询 P95 < 20 ms
- [ ] 崩溃注入 100 次轮次，`PRAGMA integrity_check` 全部 `ok`
- [ ] 备份 → 清库 → 恢复 → 数据逐条比对一致（脚本化）

### 2.3 Gate P1

在**没有任何 Flutter 代码**的前提下，用 CLI 完成一次完整生命周期：创建笔记本 → 写 1000 条笔记 → 全文搜索 → 插入附件 → 导出 Markdown → 备份 → 恢复 → 数据一致。

## 7. P6 云同步（6–10 周）

## 9. 贯穿性工作（每个阶段都做）

| 事项 | 频率 | 要求 |
|---|---|---|
| ADR | 每个架构级决策 | 决策前写，不做事后补 |

| 安全审查 | 每次涉及密钥/网络/权限 | 按《铁律》S 组逐条自检 |

## 10. 任务拆分规范（怎么写好一张任务卡）

每个任务卡必须包含：

```markdown
### <ID> <任务名>
- 目标：一句话，可验证
- 输入：依赖的任务/文档/接口
- 输出：具体文件路径或行为
- 验收：可执行命令或可观察现象（不要写"功能正常"）
- 预算：允许的时间（超 2 倍即升级求助，不硬扛）
- 风险：已知坑与回退方案
```

**禁止**的任务卡写法："完善编辑器"、"优化性能"、"处理同步问题"——没有验收标准就不能开工。

## 12. 变更控制

1. **范围变更**：新增/删除功能 → 更新本计划（含验收标准）→ 若是架构级再补 ADR → 记入变更日志。
2. **阶段延期**：连续两周进度落后 > 30% → 召开范围裁剪会（先砍 P2/P3 优先级功能，**不砍测试与数据安全**）。
3. **技术基线变更**：必须 ADR + 影响面评估 + 回退方案。
4. **紧急修复（Hotfix）**：允许绕过 Gate，但必须在 48 h 内补齐测试与文档，并在下一次复盘记录。
