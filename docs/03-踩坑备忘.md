# 1. 工具与脚本

## 1.1 PowerShell 脚本含中文却没有 UTF-8 BOM

**现象**
- 脚本突然报 `字符串缺少终止符`、`Missing expression after ','` 之类的**语法错误**，
  而代码看上去完全正常；
- 或中文输出在终端里变成乱码（`鎷惧厜绗旇`）。

**根因**
Windows PowerShell 5.1 在**没有 BOM** 时，按系统 ANSI 代码页（简体中文环境是 GBK）
解码脚本文件。UTF-8 的中文注释被按 GBK 解读后，乱码字节可能吞掉引号或括号，
于是**脚本连解析都过不去**。

**本项目实际踩了三次**：
1. `bootstrap-flutter.ps1`
2. `check-rules.ps1`
3. `coverage-gate.ps1`（这次发现了"写入工具会抹掉 BOM"这个更深的坑）

**修法**
用 UTF-8 **带 BOM** 保存 `scripts/*.ps1`。

**如何避免**
已自动化：`nested-rules` 的 **B-ENCODING** 规则会检查
"脚本含非 ASCII 字符但没有 BOM"并在 CI 中失败（附 3 个单元测试）。

⚠️ **仍然存在的陷阱**：`write` / `edit` 之类的写入工具**会抹掉 BOM**。
所以**每次用工具改完 `scripts/*.ps1`，都要补 BOM**：

```powershell
$p = 'scripts/xxx.ps1'
$t = [System.IO.File]::ReadAllText($p, [System.Text.Encoding]::UTF8)
[System.IO.File]::WriteAllText($p, $t, (New-Object System.Text.UTF8Encoding($true)))
```

改完顺手跑一次铁律检查即可发现遗漏。

## 1.2 用 Shell 命令改写文本文件会损坏编码

**现象**
用 `Set-Content -Encoding UTF8` 改写 `justfile` 后，文件里出现乱码（GBK 往返），
原本的中文注释全废。

**根因**
`Set-Content` 的编码行为与读写往返在 PS 5.1 下并不如预期：它可能先按 ANSI 读、
再按 UTF-8 写，或反之，造成不可逆的编码转换。

**修法**
用 .NET API 显式操作，或直接用编辑工具：

```powershell
$t = [System.IO.File]::ReadAllText($p, [System.Text.Encoding]::UTF8)
$t = $t.Replace('旧', '新')
[System.IO.File]::WriteAllText($p, $t, (New-Object System.Text.UTF8Encoding($false)))
```

**如何避免**
不要用 `Set-Content` / `Out-File` 改写**含中文的既有文件**。
新增文件用编辑工具；批量替换用上面的 .NET 写法。

## 1.3 首次构建像是"卡住"，其实是在下载工具链

**现象**
第一次 `cargo build` 十几分钟没有输出，看起来像死锁或卡死。

**根因**
`rust-toolchain.toml` 里声明的工具链与 `targets`（当时含
`x86_64-unknown-linux-musl`）尚未安装，rustup 正在后台下载。
输出被缓冲，因此终端上一片安静。

**修法**
等它完成；不需要的 `targets` 应当删掉（见 ADR 0005）。

**如何避免**
判断"卡住"还是"在下载"：另开一个终端看 `%USERPROFILE%\.rustup\downloads`
是否在增长，或用 `rustup show` 看已安装的目标。
不要急着 Ctrl+C——中断下载会留下半截的工具链目录。

## 1.4 .NET IO 的相对路径按"进程工作目录"解析

**现象**
一段 PowerShell 脚本明明 `cd` 到了 `client`，但
`[System.IO.File]::ReadAllText('crates/...')` 报
`未能找到路径 ... 的一部分`。

**根因**
`cd` 改变的是 **PowerShell 的位置**，而 .NET 静态 IO 用的是**进程工作目录**
（`Environment.CurrentDirectory`）。两者在 `cd` 之后不再一致。

**修法**
传绝对路径，或在脚本开头就把所有路径拼成绝对路径。

**如何避免**
批量脚本里一律用 `Join-Path $root '...'` 构造绝对路径。

## 1.5 原生命令的 stderr 会变成"终止错误"

**现象**
`coverage-gate.ps1` 在 `$ErrorActionPreference = 'Stop'` 下调用 `cargo`，
明明已经把 stderr 重定向到文件（`2> $file`），脚本却仍然抛出
`cargo.exe : warning: ... is deprecated` 并中断。

**根因**
Windows PowerShell 5.1 会把**原生命令写到 stderr 的每一行包装成 ErrorRecord**。
在 `Stop` 偏好下，这直接成为终止错误——**与是否重定向无关**。

**修法**
调用原生命令期间临时放宽偏好，并显式检查 `$LASTEXITCODE`：

```powershell
$saved = $ErrorActionPreference
$ErrorActionPreference = 'Continue'
try {
    & cargo @args 1> $outFile 2> $errFile
    $code = $LASTEXITCODE
}
finally { $ErrorActionPreference = $saved }
if ($code -ne 0) { ... }
```

**如何避免**
所有包装原生命令的脚本都按这个模式写。`$LASTEXITCODE` 才是唯一可信的判据。

## 1.6 `pwsh` 与 `just` 不是每台机器都有

**现象**
`justfile` 用 `set shell := ["pwsh", ...]` 后，本机全部任务失败（找不到 `pwsh`）。

**根因**
本机只有 Windows PowerShell 5.1（`powershell.exe`），未安装 PowerShell 7；
`just` 也没有安装。

**修法**
`justfile` 改用 `powershell`，脚本只用两者都支持的语法。

**如何避免**
不要假设开发机装了新式工具。CI 里用什么，本地就要能用什么；
不打算强制安装的工具，就不要写进必经路径。

# 2. 依赖与构建配置

## 2.1 独立 crate 不能用 `workspace = true`

**现象**
`shared/protocol` 编译报 `failed to find a workspace root`。

**根因**
该 crate 刻意**不属于** `client` 与 `server` 任何一个 workspace
（它是两端共享的纯数据契约），因此无法继承 workspace 的依赖声明。

**修法**
把它写成完全独立的清单：显式版本 + 自己的 `[workspace]` 段。

**如何避免**
"共享 crate" 不等于 "workspace 成员"。要共享**契约**就别共享**依赖图**
（理由见 2.2）。

## 2.2 把两个 workspace 合并会让依赖版本被互相拖低

**现象**
客户端原本用 `rusqlite 0.40.2`，合并 workspace 后变成 `0.32.1`。

**根因**
Cargo 在**同一个依赖图**内会为同一个 crate 选出一个版本。
服务端的 `sqlx` 通过 `libsqlite3-sys` 施加了约束，把 `rusqlite` 一起拖了下来。

**修法**
拆成两个独立 workspace（`client/` 与 `server/`），各自持有 `Cargo.lock`。
记录在 ADR 0002。

**如何避免**
两端依赖差异大时，**默认拆分 workspace**。合并的代价不会立刻显现，
而是在某次依赖升级时以"版本莫名回退"的形式出现。

## 2.3 `cargo generate-lockfile` 之后要提交 lock

**现象**
新增依赖后忘记提交 `Cargo.lock`，CI 解析出不同版本。

**修法**
凡改动 `Cargo.toml` 依赖，一律 `cargo generate-lockfile` 或 `cargo build`
并**提交 lock 文件**（铁律 B1）。

## 2.4 clippy 不允许在 `#[test]` 上写 `#[allow]`

**现象**
想给测试代码单独放开 `unwrap_used`，但 `#[allow]` 被报 `useless attribute`。

**根因**
clippy 的 `unwrap_used` / `expect_used` / `panic` 是 **crate 级** lint
（由 `clippy::restriction` 提供），不允许在函数/模块上定向豁免。

**修法**
workspace 里把它们设为 `allow`，另用 `nested-rules` 的 R1 规则
（只扫 `src/` 且跳过 `#[cfg(test)]`）兜底。见技术债 #1。

**如何避免**
不要把"clippy 全绿"当成"没有 unwrap"的证据——两道门禁的覆盖面不同。

## 2.5 `forbid(unsafe_code)` 无法被生成代码豁免

**现象**
`flutter_rust_bridge` 生成的文件需要 `unsafe`，而 crate 级
`#![forbid(unsafe_code)]` 让编译失败，且**子模块无法覆盖 `forbid`**。

**修法**
workspace 级 lint 从 `forbid` 改为 `deny`；每个手写 crate 自己写
`#![forbid(unsafe_code)]`；只有 FFI crate 显式 `allow` 并写明理由。

**如何避免**
`forbid` 是"绝对不可覆盖"，只在**确定整棵子树都不需要**时使用。

# 3. Windows 平台特性

## 3.1 Windows 上不能删除仍被打开的文件

**现象**
`tempDir.deleteSync(recursive: true)` 抛
`PathAccessException: Deletion failed ... OS Error 32: 另一个程序正在使用此文件`。

**根因**
SQLite 连接（以及 WAL 文件）仍被 Rust 引擎持有。POSIX 允许删除已打开的文件，
**Windows 不允许**。

**修法**
显式关闭引擎（`engine_close()`）后再删除；它会顺带
`PRAGMA wal_checkpoint(TRUNCATE)` 把 WAL 合并回主库。

**如何避免**
任何"清理临时目录"的代码都要先释放文件句柄。
这条也让"拷贝整个数据目录即完整备份"成为可靠的用户直觉。

## 3.2 Windows 上数据目录由可执行文件的版本资源决定

**现象**
把 `windows/runner/Runner.rc` 里的 `CompanyName` / `ProductName` 改成中文品牌名后，
应用**读到空库**——数据目录从
`%APPDATA%\app.nestednote\nested` 变成了
`%APPDATA%\NestedNote\拾光笔记 NestedNote`。

**根因**
Flutter 的 `getApplicationSupportDirectory()` 在 Windows 上返回
`%APPDATA%\<CompanyName>\<ProductName>`，而这两个值来自 exe 的**版本资源**。
也就是说：**改一个 `.rc` 字段就会移动用户数据目录**。

**修法**（本项目最终采用）
- 取值依据《项目章程》§1.2：**反域名作公司名、工程标识作产品名**，得到
  `%APPDATA%\app.nestednote\nested\nested.db`——既符合章程，又保持纯 ASCII；
- 在 `Runner.rc` 与 `client/apps/flutter/tool/app_paths.dart` **两处**写明这条因果关系；
- 命令行工具与 `path_provider` 必须使用**同一份路径规则**，否则会出现
  "脚本写进 A 目录、应用从 B 目录读"的假故障（本项目也踩过）。

**如何避免**
- 产品已经发布后再改产品名 = 用户数据"消失"。若必须改，需提供迁移逻辑：
  启动时检测旧目录并搬迁；
- **不要出现"章程写一个路径、程序用另一个路径"**的情况。本项目为此专门做了一次对齐
  （章程 §1.2 与 §1.4 规定的路径以前与实现不符）。

## 3.3 MSVC 在中文 Windows 上按 ANSI 解读无 BOM 的源码

**现象**
`main.cpp` 里写入中文窗口标题后编译异常或显示乱码。

**根因**
MSVC 在**没有 BOM** 时按系统 ANSI 代码页（GBK）解读源码，
UTF-8 的中文字节被错误解释。与 1.1 是同一类问题，只是发生在 C++ 侧。

**修法**
窗口标题改用 **`\u` 转义**（`L"\u62fe\u5149..."`），彻底摆脱源码编码依赖。
这是比"记得加 BOM"更稳的做法——它不依赖任何人的记性。

**如何避免**
C++ 源码里的非 ASCII 字符串，优先考虑转义或资源文件。

见 4.5。

# 4. Flutter ↔ Rust（FFI / FRB / Cargokit）

## 4.1 crate 名里带连字符会让 codegen 与 Cargokit 全部失灵

**现象**
`flutter_rust_bridge_codegen integrate` 报 `Not a valid package name: "null"`。

**根因**
原 crate 名是 `nested-app`。**连字符在 Dart 包名里非法**，
codegen 与 Cargokit 都要求"crate 名 = Dart 包名 = 输出库名"，于是全部对不上。

**修法**
统一为下划线命名 `nested_app`：crate 名、Dart 包名、Cargokit 目标名、
gradle 配置、podspec 文件名、AndroidManifest 包名**全部一致**。

**如何避免**
项目命名阶段就定下"Rust crate 与 Dart 包同名且只用下划线"。

## 4.2 Cargokit 期望的 CMake 变量名与工程名必须完全一致

**现象**
`nested_app.dll` 编译成功，但没有被拷贝进应用目录，运行时报找不到动态库。

**根因**
`rust_builder/windows/CMakeLists.txt` 导出的是 `${PROJECT_NAME}_bundled_libraries`
（值为 `nested-app_...`），而 Flutter 生成的 `generated_plugins.cmake` 读的是
**`nested_app_bundled_libraries`**。变量名对不上，链接步骤就被静默跳过。

**修法**
显式导出正确的变量名：

```cmake
set(nested_app_bundled_libraries "${nested_app_cargokit_lib}" PARENT_SCOPE)
```

**如何避免**
"编译成功但运行期找不到库"这类问题，第一个要查的就是
**产物是否真的出现在 exe 同目录**（`build\windows\x64\runner\Release\`）。

## 4.3 `mod frb_generated;` 必须是第一个 item

**现象**
把 `mod frb_generated;` 插到文件顶部后，编译报错——crate 级文档注释
（`//!`）与内部属性（`#![...]`）失效。

**根因**
Rust 的内部属性与内部文档注释**只能出现在文件最前面**。
把 `mod` 声明插到它们之前，会让它们不再位于"文件开头"。

**修法**
保持顺序：`//!` 文档 → `#![...]` 内部属性 → `mod frb_generated;` → 其余 item。

**如何避免**
生成代码的插入位置要看**语言规则**，不能凭"放最前面最显眼"的直觉。

## 4.4 `flutter test` 读不到动态库（error 126）

**现象**
`flutter test` 报 `Failed to load dynamic library 'nested_app.dll' (error code: 126)`。

**根因**
FRB 的默认加载器按**相对运行时的当前目录**查找 `../rust/target/release/`，
在 `flutter test` 下这个相对路径不可靠。

**修法**
先构建 release 动态库，并显式给出绝对路径：

```powershell
cd client; cargo build --release -p nested_app
$env:FRB_DART_LOAD_EXTERNAL_LIBRARY_NATIVE_LIB_DIR = "$PWD\target\release"
cd apps/flutter; flutter test
```

**如何避免**
真实应用不走这条分支（Cargokit 会把库放进应用目录，靠 Windows 的
DLL 搜索顺序从 exe 同目录加载），因此这是**测试环境专有**的配置问题。

## 4.5 测试里用 `path_provider` 会因平台通道缺失而失败

**现象**
集成测试报 `Binding has not yet been initialized`。

**根因**
`path_provider` 依赖平台通道，而 `flutter test` 环境里没有。
`getApplicationSupportDirectory()` 因此不可用。

**修法**
把"解析数据目录"与"启动引擎"拆开：测试直接调用
`startEngineInDirectory(临时目录)`，不经过 `path_provider`。

**如何避免**
凡是依赖平台通道的调用，都要留一个"可注入"的入口供测试使用。

## 4.6 `RustLib.init()` 不允许重复调用

**现象**
刷新自检（`ref.invalidate(engineProvider)`）后应用崩溃：
`StateError: Should not initialize flutter_rust_bridge twice`。

**根因**
FRB 的 `initImpl` 会检查 `__state != null` 并**抛异常**。

**修法**
加幂等保护：

```dart
bool _rustInitialized = false;
Future<void> ensureRustInitialized() async {
  if (_rustInitialized) return;
  await RustLib.init();
  _rustInitialized = true;
}
```

**如何避免**
任何"初始化"API 都要先确认它是否幂等，不要假设。

## 4.7 FFI 导出面会被"顺手 pub"污染

**现象**
测试辅助函数 `engine_lock_for_tests` 出现在生成的 Dart API 里。

**根因**
`flutter_rust_bridge` 的代码生成**只看可见性，不看 `#[doc(hidden)]`**。

**修法**
用 `#[cfg(test)]` 把它彻底排除在非测试构建之外。

**如何避免**
跨语言契约必须逐项审查（铁律 A3）。`#[doc(hidden)]` 不是访问控制。

## 4.8 改完 Rust API 必须重新生成绑定

**现象**
编译报 `cannot find function ... in module`，报错文件却是
`frb_generated.rs`（生成代码）。

**根因**
生成文件不入库，且它按**旧版 Rust API** 生成。

**修法**
`powershell -NoProfile -File scripts/generate-ffi-bindings.ps1`。

**如何避免**
只要改动了 `apps/rust/src/api/**`，就必须重新生成——
脚本会同时校验生成的代码格式化后是幂等的。

# 5. SQLite 与数据一致性

## 5.1 SQLite 连接没关会让 Windows 拒绝删除数据目录

见 3.1（同一根因的两个表现）。

## 5.2 同步队列的外键指向单张表，会在写入其它实体时失败

**现象**
给 `sync_operations` 补入队逻辑后，创建笔记本立刻报
`787 FOREIGN KEY constraint failed`。

**根因**
`0001_init.sql` 把 `sync_operations.note_id` 定义为
`REFERENCES notes (id)`，但这张表在语义上是**通用实体变更队列**
（铁律 T3 要求任何本地写都入队，包括笔记本与标签）。
把笔记本 id 写进带外键的 `note_id` 必然失败。

**这个缺陷一直存在，只是因为"此前只有笔记更新入队"而从未暴露。**

**修法**
新增迁移 `0002_sync_operations_entity.sql`：列改名 `entity_id`、
**去掉外键**（SQLite 无法表达"多态外键"），引用完整性由写入路径保证；
存量数据用 `LEFT JOIN notes` 清洗悬空引用后原样保留。

**如何避免**
设计"通用队列/日志表"时，不要给"指向具体实体"的列加外键——
先问清楚这一列是否只服务一种实体。

## 5.3 持有连接借用时再取连接会**静默死锁**

**现象**
测试进程**挂住**：不报错、不 panic、CPU 接近 0，就是不动。
（本项目真实发生过，排查花了很久。）

**根因**
`Database::connection()` 返回 `MutexGuard`，而 `std::sync::Mutex` **不可重入**。
在持有 guard 期间调用任何内部会取连接的 `Database` 方法
（`check_integrity`、`with_transaction`、`setting`…）就是自己等自己。

**修法**
- 加 `AtomicBool` 重入检测，误用立即返回 `DbError::ReentrantLock`（**报错而不是挂起**）；
- 提供 `with_connection(|c| ...)` 闭包 API 作为推荐用法；
- `ConnectionGuard` 在 `Drop` 时复位标志，避免标志泄漏。

**如何避免**
"锁 + 返回 guard"的 API 天生有这个陷阱。要么收成闭包式，要么加重入检测。
**"静默挂起"比"报错"危险得多**——后者只是失败，前者会耗掉一整天。

## 5.4 `IMMEDIATE` 与 `DEFERRED` 的差别不是风格问题

**现象**
WAL 模式下偶发 `SQLITE_BUSY`，而且 `busy_timeout` 似乎不生效。

**根因**
`DEFERRED` 事务到**第一次写**才尝试取写锁。若事务是"先读后写"
（保存路径正是：先更新 `notes`、再写 `documents`），取锁发生在中途；
此时若另一连接持有写锁，SQLite 立刻返回 `SQLITE_BUSY`——
而 **`busy_timeout` 对"锁升级失败"不生效**。于是表现为"随机失败"而不是"等一会儿"。

**修法**
统一用 `IMMEDIATE`：一开始就取写锁，冲突发生在起点，由 `busy_timeout` 正常排队。
参数用 `&mut Connection`，顺带让**嵌套事务在编译期不可能**。

**如何避免**
不要混用两种事务行为。统一到一个辅助函数里，并在注释里写清为什么。

## 5.5 用"现有版本号"当坏迁移会被判为无需升级

**现象**
测试"迁移失败必须回滚"时，坏迁移根本没执行，断言失败。

**根因**
测试里把版本 2 当作坏迁移，但真实清单里版本 2 已经存在，
`apply` 的 `from == latest_version` 分支把它判定为"无需升级"并直接返回。

**修法**
坏迁移必须**追加在全部已发布迁移之后**（版本 `LATEST_VERSION + 1`）。

**如何避免**
写"失败路径"测试时，先确认被测分支**真的会进入**。

## 5.6 已发布的迁移文件不可修改

**现象**
改了 `0001_init.sql` 后，测试报哈希不匹配。

**根因**
迁移哈希护栏（`tests/migration_guard.rs`）会校验每个迁移文件的 SHA-256。

**修法**
新增一个 `NNNN_name.sql` 并登记到 `MIGRATIONS`，同时更新哈希清单。
**绝不要**为了让哈希通过而改清单里的旧哈希。

**如何避免**
这是因为：用户库已按旧版迁移过，事后改文件会让"新装用户"与"老用户"的
schema **悄悄分叉**——这类问题只在生产爆雷。见 ADR 0003。

## 5.7 文档元数据的易变字段会让"内容是否变化"永远为真

**现象**
修完"无变更不产生修订"后，测试仍显示：**内容一模一样的第二次保存
照样递增了版本**。

**根因**
`DocumentMetadata` 含 `created_at_ms` / `updated_at_ms`，而
`Document::from_blocks(blocks, at_ms)` 每次都带**新的时间戳**。
于是"同样的正文构造两次"产生**不同的序列化字节**。

我最初把"内容是否变化"实现成**字节比较**——它永远返回"变了"，
等于这个判断形同虚设。

**修法**
只比**语义内容**（`Document::has_same_content` 只比 `blocks`），
并让文档元信息跟随笔记时间戳（`align_timestamps`）。

**如何避免**
判断"两份数据是否等价"时，先问：**这里面有没有每次都会变的字段？**
时间戳、随机 id、版本号——有它们就不能用全量相等。

## 5.8 进程被强杀会留下 `-wal` / `-shm` 文件

**现象**
数据目录里出现 `nested.db-wal`（0 KB）与 `nested.db-shm`（32 KB），
即使应用已经关闭。

**根因**
SQLite 的 WAL（预写日志）模式下，写入先进 `-wal`，满足条件才合并回主库。
若进程**被强制终止**（`Kill()`、任务管理器结束进程、断电），
就来不及做 checkpoint，于是留下这两个文件。

**数据安全吗——安全**。SQLite 下次打开同一数据库时会**自动恢复** WAL 里的内容，
这是 WAL 的设计保证，不需要人工干预。

**但它影响两件事**：
1. 用户"拷贝数据目录即完整备份"的直觉——**必须连 `-wal` 一起拷**，只拷 `.db` 会丢最近的修改；
2. 目录看起来"不干净"。

**修法**
`engine_close()` 会执行 `PRAGMA wal_checkpoint(TRUNCATE)` 把 WAL 合并回主库并清空它。
这是"显式关闭"存在的第二个理由（第一个是释放文件锁，见 3.1）。

**如何避免**
- 应用退出路径要**尽可能**走显式关闭；
- 但不要假设一定能走到——`Kill()` 与断电不给机会。因此**备份逻辑必须包含 `-wal`**，
  而不是依赖"关闭时已经合并"。

## 5.9 跨两处存储的写入，"顺序"本身就是正确性的一部分

**现象**
实现"把附件挂到笔记上"时，代码看起来合理（写文件 → 写元数据 → 更新笔记），
但实际运行时报 `Database(ReentrantLock)`；
改好之后又要面对一个新问题：文件写成功、元数据写入失败时怎么办？

**根因（两层）**

1. **顺序陷阱**：同一段代码里先 `database().connection()`、
   再调 `core.device_id()`——而后者内部**也要取连接**，于是重入。
   这正是 [5.3](#53-持有连接借用时再取连接会静默死锁) 那个坑，
   只不过这次被重入检测**当场拦下**（返回错误而不是挂起）。
   如果没有那个检测，这里就是一次静默死锁。
2. **架构层面的顺序**：文件系统与数据库**无法共享一个事务**，
   因此必须明确哪一半先落。选错的代价不对称：

   | 顺序 | 失败残留 | 后果 |
   |---|---|---|
   | 先文件后库 | 孤儿文件 | 安全：占点磁盘，GC 可回收 |
   | 先库后文件 | 断链 | **危险**：读取报错，用户看到"附件损坏" |

**修法**
- 固定为**先文件后库**，并把这个不变量写成文档与测试：
  "每一条元数据记录，其内容一定已完整落盘"；
- 反向（有文件无记录）允许存在，由带**宽限期**的 GC 回收
  （宽限期是必需的：它覆盖"文件已写、元数据还没写"的中间态）；
- 取连接的顺序写进注释：**先把所有需要数据库的辅助值拿到手，再取连接**。

**如何避免**
- 设计跨存储的写路径时，**先问"失败时哪一半会残留"**，再决定顺序。
  判据是：**让残留物是"可回收的垃圾"，而不是"用户可见的故障"**；
- 任何"先 A 后 B"的约束都要写成测试。只写在注释里的顺序，
  下一个人重构时就会改掉；
- 遇到需要多个数据库派生值的地方，把它们**一次性取完**再进临界区。

## 5.10 固定测试时间与真实文件时间混用

**根因**
测试用常量 `NOW = 1_700_000_000_000`（2023-11-14）当"现在"，
而文件 mtime 来自**真实的系统时钟**（2026）。
于是 `now_ms - mtime` 是**负数**，`saturating_sub` 归零 →
每个文件都被判为"刚写入、在宽限期内"。

这与 [5.7](#57-文档元数据的易变字段会让内容是否变化永远为真) 是**同一类错误**：
把两种不同的时间来源放进同一个比较里。

**修法**
需要与文件时间比较的测试，必须取**真实系统时间**作为基准：

```rust
let real_now = i64::try_from(
    SystemTime::now().duration_since(UNIX_EPOCH).unwrap().as_millis()
).unwrap();
```

**如何避免**
只要代码里出现了"文件时间 / 进程时间 / 系统时间"，就先确认
**它们是不是同一个时间源**。固定常量适合测"逻辑"，不适合测"时间比较"。

# 7. 测试与验证

## 7.1 进程级单例 + cargo 并行测试 = 互相覆盖

**现象**
`cargo test` 报 `NOT_FOUND`：**刚创建的笔记在下一个调用里就找不到了**。
看起来像数据丢失，串行执行（`--test-threads=1`）却全过。

**根因**
引擎是**进程级单例**（Flutter 侧只有一个内核），而 `cargo test` 默认**并行**。
任意一个测试调用 `engine_start` 都会把别的测试正在使用的引擎**替换掉**。

**修法**
加一把全局测试锁，**两个测试模块共用**：

```rust
#[cfg(test)]
pub(crate) mod test_support {
    pub(crate) fn engine_lock() -> MutexGuard<'static, ()> { /* ... */ }
}
```

**如何避免**
设计全局单例时，**同步**考虑它的测试隔离方案。
另外注意：`branding` 的测试也会启动引擎（因为 `start_engine` 委托给了它），
所以"只给新模块加锁"是不够的。

## 7.2 dll 名不一致导致的 `error 193` 与 `error 126`

**现象**
动态库加载失败。`error 126` 通常是"找不到库"，
`error 193`（`不是有效的 Win32 应用程序`）则是**加载到了错误的文件**。

**根因**
库文件名、Cargokit 目标名、Dart 侧期望名三者不一致；
或架构不匹配（在 x64 进程里加载了 32 位库）。

**修法**
统一命名为 `nested_app.dll`（见 4.1、4.2）。

**如何避免**
排查顺序：① 库是否**真的存在**于 exe 同目录；
② **架构是否匹配**；③ 依赖的其它 dll 是否齐全。

## 7.3 远程/虚拟化环境下截屏可能返回恒定同一帧

**现象**
连续多次截图，**文件哈希完全相同**——包括界面内容明明已经变化时。
更糟的是有时还会截到**别的窗口**（本项目实测截到了另一个应用的界面）。
因此"截图看起来对"不能作为验收证据。

**根因**
远程桌面 / 虚拟化环境的屏幕抓取可能返回缓存帧、捕获不到目标窗口，
或抓到 Z 序在前但并非目标的窗口。

**修法**
让**应用自己报告它看到了什么**，写成可由脚本断言的文件：

```
%TEMP%\nested-ui-diagnostics.txt
noteCount=4
noteTitles=[示例]读书记录 | [示例]内容寻址存储 | ...
```

因为 `noteTitles` 是在构建列表项时取的，它能证明列表 widget 确实拿到了数据。

**如何避免**
UI 验收优先选**可断言的输出**（日志、状态文件、测试断言），
把截图当作辅助说明而非依据。

## 7.4 引擎单例的测试锁要覆盖所有会启动引擎的测试

见 7.1 的"如何避免"。

## 7.5 把"失败"静默转成"空结果"会让故障伪装成"没有数据"

**现象**
三栏界面的左栏一直显示"还没有笔记本"，而数据库里明明有 5 个。
排查方向一度跑偏到"数据目录不对""打开的是另一个库"。

**根因**
FFI 函数的签名是 `pub fn notebooks_tree() -> Vec<NotebookNode>`，
失败时返回**空 `Vec`**：

```rust
match with_core(|core| { /* ... */ }) {
    Ok(nodes) => nodes,
    Err(_) => Vec::new(),   // ← 错误在这里被吞掉
}
```

于是"查询失败"与"确实没有笔记本"在界面上**长得一模一样**。
用户看到"还没有笔记本"，会以为**数据丢了**——这是最糟的一类误导。

**修法**
改成返回 `NoteResult`（与其它 API 一致），失败带上错误码与提示：

```rust
Ok(nodes) => NoteResult::ok(NotePayload { notebooks: nodes, ..Default::default() }),
Err(failure) => failure,
```

界面侧对应地**如实抛出**，而不是退化成空列表。
改完立刻就看到了真实错误，问题随即定位。

**如何避免**
1. **"空"与"失败"必须是两个不同的结果。** 任何"查询列表"的接口，
   都要有办法区分"查到了 0 条"和"没查成"；
2. 写 `Err(_) => 默认值` 之前，先问：**这个默认值会不会伪装成合法结果？**
   空列表、0、空串都属于危险默认值；
3. 这条与铁律 E1（错误必须在边界处翻译而不是丢弃）是同一个要求，
   只是"翻译"很容易被写成"替换成空值"。

## 7.6 观测代码本身也会失效——先确认"看得见"再下结论

**现象**
排查界面为何是空的时，我在页面里加了诊断输出，结果**诊断文件里始终没有
那一段**。于是我判断"数据确实没加载出来"，继续往数据层深挖。

**根因**
诊断写在 `WidgetsBinding.addPostFrameCallback` 里，而这个回调
**只在"页面重建"之后排队**。当时 `NotesPage.build` 只 watch 了
`engineProvider`（且用 `switch` 读 `.value`），数据变化并不触发它重建——
**回调从第二次起就不会再排队了**。

也就是说：不是数据没出来，而是**我的观测手段一次都没被触发**。

**修法**
把观测挂到真正会变化的东西上：`ref.listen(provider, ...)`。
它直接订阅 provider，不依赖"页面是否重建"。

**如何避免**
- **在做结论前，先证明观测本身是活的**：让诊断输出带时间戳与调用次数，
  确认它真的在按预期触发。本项目后来给快照加了 `at=` 时间戳才发现只触发了一次；
- 观测代码优先放在**数据层**（provider 订阅）而不是**展示层**（帧回调）：
  前者与数据变化同步，后者与渲染时机绑定，两者不是一回事；
- 顺带一条：诊断代码出错不该影响功能，但也**不该静默吞掉**——
  否则你会在"以为是数据问题"和"其实是诊断问题"之间反复横跳。

## 7.7 界面侧的"封顶"不要封掉层级的区分度

**现象**
左栏是多层级笔记本树，缩进按深度递增。但第 7 层开始缩进**不再变化**，
于是两个不同层级的节点看起来一样深，用户无法判断自己在哪一层。

**根因**
缩进写成 `depth.clamp(0, 6) * 14`——本意是"别让深层级把名称挤出可视区"
（这个担心是对的，左栏宽度固定），但 clamp 的**对象搞错了**：
它封的是"层级的区分度"，而不是"缩进总宽度"。

**修法**
封总宽度，不封层级：

```dart
double notebookIndent(int depth) {
  final wanted = kIndentBase + (depth < 0 ? 0 : depth) * kIndentPerLevel;
  return wanted > kIndentMax ? kIndentMax : wanted;   // 只封顶，不压平
}
```

这样在上限之前**每一层都有不同的缩进**（本项目实测可区分到第 9 层），
再深才稳定在上限。同时把缩进提取成**纯函数**，便于直接断言——
缩进是层级可视化的核心，藏在 widget 里几乎没法测。

**如何避免**
- 写 `clamp` 之前先确认：**我要限制的是"总量"还是"粒度"？**
  限制总量是安全的（防溢出），限制粒度会**丢信息**（层级、优先级、精度）；
- 任何"表达层级/顺序"的视觉量（缩进、颜色深浅、字号），
  都要保证**相邻层级可区分**，这应当写成测试而不是靠肉眼；
- 相关：数据层**不加**层级限制，界面层**必须**有视觉上限——
  两者不是矛盾，而是"能力"与"呈现"的分工。数据层限制深度会丢失用户数据，
  界面限制缩进只是显示取舍。

# 8. 门禁与指标

## 8.1 对占位 crate 一刀切卡覆盖率等于自欺

**现象**
如果对**全部** crate 要求行覆盖率 ≥ 80%，那么只有类型与常量、
没有实现的 crate（例如 `nested-import` 只有 8 行）会因为
"可执行代码极少"而**轻松达标**，指标好看但没有意义。

**修法**
门禁清单**显式列出**"已实现的 crate"，每一项豁免都写明原因与解除条件，
并且**全部** crate 的数字都会打印出来（避免"看不见"）。
写在 `scripts/coverage-gate.ps1` 头部注释里。

**如何避免**
覆盖率度量的是"已实现代码被验证了多少"。
对"尚未实现"的代码谈覆盖率没有意义——要诚实地把它标出来。

## 8.2 生成的代码要排除在覆盖率之外

**现象**
FFI crate 的覆盖率被 `frb_generated.rs`（不入库、覆盖率恒为 0%）拖到很低。

**修法**
`--ignore-filename-regex 'frb_generated\.rs$'`。

## 8.3 规则检查器的误报会让人开始绕过门禁

**现象**
`nested-rules` 把 `scripts/check-ci.ps1` 里的文档行
（`$env:GITHUB_TOKEN = "<个人访问令牌>"`）当成硬编码凭据。

**修法**
跳过 `scripts/` 与 `tools/nested-rules` 自身，并**写明这个取舍的代价**：
脚本目录内的**真实**凭据不会被这条规则拦住。

**如何避免**
门禁一旦经常误报，开发者就会开始绕过它——那时门禁的实际价值是负的。
宁可缩小范围并把代价写清楚，也不要留一堆假警报。

## 8.4 CI 里缺生成步骤会让 `cargo fmt --check` 失败

**现象**
CI 报 `Error writing files: failed to resolve mod 'frb_generated'`。

**根因**
生成文件不入库，而 `cargo fmt` 需要先能解析所有模块。

**修法**
在格式检查**之前**加一步生成绑定；而生成需要 Flutter 工具链
（`flutter_rust_bridge_codegen generate` 要求 Dart/Flutter 可用），
因此 CI 还要先装 Flutter 并固定版本。

**如何避免**
"生成物不入库"是有代价的：**每个消费它的步骤都要先能生成它**。
把这条依赖链在 CI 里显式画出来。

# 9. 文档与协作

## 9.1 注释里宣传的任务并不存在

**现象**
`justfile` 头部注释写着 `just check-client`、`just check-server`，
但这两个任务**根本没有定义**。

**修法**
补齐任务，并把"文档必须与实现一致"写进日常检查。

**如何避免**
描述"有什么"的文字，最容易被复制粘贴而不被验证。
凡是"我们支持 X"这类断言，要么有命令可跑，要么不要写。

## 9.2 一行注释里的行号会漂移

**现象**
设计文档大量引用 `block.rs:333` 这类行号，改动代码后全部失效。

**修法**
三份设计文档在文末都标注了"撰写基线"（对应哪个 commit）。
按铁律 M3，改动公共行为时同步刷新对应小节。

**如何避免**
引用行号时同时**引用符号名**（函数名/类型名），
这样即使行号漂移，读者仍能定位。

## 9.3 多行 commit message 要用文件

**现象**
`git commit -m "多行中文含引号"` 报
`pathspec ... did not match`。

**修法**
把信息写入文件后 `git commit -F <文件>`。

**如何避免**
凡是超过一行的提交信息，一律走文件。

## 9.4 照抄"规划清单"当最终编号会导致整体错位

**现象**
技术文档 §48 列了一份"建议的下一份技术文档"清单：

```text
03-项目总体架构.md
04-Rust-Core架构设计.md      ← 照抄了这个
05-SQLite数据库设计.md        ← 照抄了这个
06-Document-Model设计.md      ← 照抄了这个
07-Flutter项目架构.md
...
```

实现时照着抄，于是三份设计文档编号成了 `04`/`05`/`06`——
**既与"03 是项目总体架构"的预留冲突，整体又比规划低了一格**。
后来新增"踩坑备忘"想用 `03` 时才发现撞号。

**根因**
那份清单是**规划建议**，不是最终编号：
- 它缺少"工程化与仓库结构"这一项，导致后续整体顺延；
- 它没有说明"`03` 已被预定"这件事在实现时是否仍然成立。

**修法**
趁引用还少（14 处）时统一修正：
- 三份文档重命名为 `05`/`06`/`07`；
- `docs/design/README.md` 建立**编号登记表**，并写明"本表是权威，技术文档 §48 是建议"；
- 在技术文档 §48 的清单上也标注"编号以登记表为准"。

**如何避免**
1. **编号类信息必须有唯一权威源**。本项目其它地方已经这么做了
   （品牌名 → `nested_core::branding`；schema → 迁移文件），编号却漏了；
2. **开新文档前先占位**，而不是事后补登记；
3. 规划文档里的"建议清单"要显式标注它是建议——否则下一个人还会照抄。

**这条坑的普遍形态**：**把"某个文档里的示例"当成"必须遵守的规范"**。
示例与规范混在一起时，读的人无法分辨，于是照抄示例反而错。

# 11. 尚不能自动化的坑（只能靠人记）

这些依赖**判断**而非模式匹配，因此写在这里提醒：

1. **数据目录随版本资源漂移**（3.2）：改 `Runner.rc` 前想一想用户数据。
   另外注意章程与实现可能不一致——本项目为此专门对齐过一次。
2. **全量相等不等于语义相等**（5.7）：比较前先问"有没有每次都变的字段"。
3. **"编译成功但运行期找不到库"**（4.2）：先查产物是否真的在 exe 同目录。
4. **"算错了"而不是"报错了"**（5.2、5.7、5.10）：这类问题不会让程序崩溃，
   只会让结果悄悄变错。**写完判断逻辑后，要专门构造"应当保持不变"的用例。**
   本项目修 #11 时，第一版实现看起来对、测试却证明它完全没生效（5.7）；
   写 GC 测试时又因为时间源不一致而让断言永远成立（5.10）。
5. **合并依赖图的长期代价**（2.2）：合并时不痛，升级时才痛。
6. **单例设计的测试隔离**（7.1）：设计单例时就要同步想好怎么测它。
7. **示例被当成规范**（9.4）：读规划文档时先分清"这是建议还是规定"。
8. **"静默失败"比"报错"危险得多**（5.3）：设计 API 时，宁可让它报错，
   也不要让它挂住或悄悄返回错误结果。
9. **跨两处存储的写入顺序**（5.9）：判据是"让残留物是可回收的垃圾，
   而不是用户可见的故障"。
10. **同一类错误会反复出现**：5.7 与 5.10 表面是两个不同的问题
    （文档元数据 vs 文件时间），本质是同一个——
    **把两类不同的东西放进同一个比较**。写判断逻辑时先问：
    "我比较的这两样，真的是同一类东西吗？"

# 12. 开工前的检查习惯

把上面散落的教训收敛成几个**可以养成的动作**：

## 12.1 动手前

- [ ] 这次要碰的东西，速查索引里有对口条目吗？（尤其 `scripts/*.ps1`、`.rc`、迁移、FFI）
- [ ] 要写"判断两者是否相同"的逻辑吗？→ 先确认里面有没有易变字段（5.7）
- [ ] 要比较时间吗？→ 确认参与比较的是不是**同一个时间源**（5.10）
- [ ] 要跨两处存储写入（文件 + 数据库）吗？→ 先决定失败时哪一半残留（5.9）
- [ ] 要加全局状态（单例/缓存）吗？→ 测试怎么隔离（7.1）
- [ ] 要新增文档编号吗？→ 先去 `docs/design/README.md` 登记表占位（9.4）
- [ ] 要改已发布的迁移/契约吗？→ 铁律 Q2 / A10；新增而不是修改

## 12.2 写完代码后

- [ ] **专门构造"应当保持不变"的用例**——这是"算错了"类问题的唯一防线
- [ ] **有没有 `Err(_) => 空值/默认值`？** 先问它会不会伪装成合法结果（7.5）
- [ ] 加了诊断/日志？→ 先确认它**真的被触发**（带时间戳或计数）（7.6）
- [ ] 涉及数据库的方法里，**所有派生值的获取是否都在取连接之前**？（5.9 第 1 层）
- [ ] 改过 `scripts/*.ps1` 吗？→ 补 UTF-8 BOM（1.1），然后跑 `just check-rules`
- [ ] 改过 `apps/rust/src/api/**` 吗？→ 重新生成 FFI 绑定（4.8）
- [ ] **改了 FFI 结构体字段吗？** → 记得**重建 release 动态库**再跑 Flutter 测试，
  否则测试用的是旧库，会以"解码失败"的形式报错（4.8 的连带坑）
- [ ] 改了公共行为吗？→ 同一个提交里更新对应设计文档（铁律 M3）
- [ ] 出现"文档说 A、代码做 B"吗？→ 修掉其中一个，不要留着（9.1）

## 12.3 遇到"卡住/失败"时

先按这个顺序缩小范围，能省很多时间：

| 症状 | 第一个要查的 |
|---|---|
| 进程静默挂起，不报错 | 死锁 / 重入锁（5.3）；先看线程栈或用超时打断 |
| 构建"卡住"很久 | 是不是在下载工具链（1.3）？看 `.rustup\downloads` 是否增长 |
| 动态库加载失败 | 库是否在 exe 同目录 + 架构是否匹配（7.2） |
| 数据"丢了" | 数据目录是否变了（3.2）；旧目录是否还在 |
| 测试单跑能过、全量失败 | 全局状态互相干扰（7.1） |
| 界面显示"空"，但怀疑有数据 | 先看是不是"失败被转成了空结果"（7.5） |
| 加的诊断/日志没输出 | 先确认观测本身有没有被触发（7.6） |
| 不同层级看起来一样深/一样大 | `clamp` 封错了对象：封了粒度而不是总量（7.7） |
| 中文乱码/脚本语法错 | 编码（1.1）；PS 脚本看 BOM，C++ 源码看 BOM |
| 截屏与预期不符 | 先别信截屏（7.3），找可断言的输出 |
| 结果悄悄不对但没报错 | 8 成是"比较/判断"逻辑把易变字段算进去了（5.7） |
