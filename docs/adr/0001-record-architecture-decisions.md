# ADR 0001：使用架构决策记录（ADR）

- **状态**：已接受
- **日期**：项目 P0 阶段
- **决策者**：项目负责人

## 背景

本项目在架构、数据格式与协议上会持续做出难以逆转的决策（例如"用块模型而不是 HTML"、
"先做修订日志而不是 CRDT"）。这类决策如果只存在于聊天记录或某个人的记忆里，
半年后没人知道"为什么当初这么设计"，于是要么重复讨论，要么在不了解约束的情况下推翻它。

《工程铁律》M2 要求：换库、换协议、改数据格式、偏离铁律都必须有 ADR。

## 决策

在 `docs/adr/` 下使用**编号 + 标题**的 Markdown 文件记录每一项架构决策，
采用业界通行的轻量格式（状态 / 背景 / 决策 / 备选方案 / 后果），并且：

1. **决策前写**，不是事后补。ADR 的价值在于"迫使在动手前想清楚备选方案"。
2. **不修改已接受的 ADR**：改变主意时新写一份，并把旧的标为"被 NNNN 取代"。
   这与迁移文件不可变是同一个道理——历史必须可追溯。
3. 文件命名：`NNNN-短横线小写标题.md`，编号从 `0001` 起连续递增。

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| 不写 ADR，靠代码注释 | 注释只能记录"是什么"，难以记录"为什么不选另一个"，且散落各处 |
| 用 Wiki / 外部知识库 | 与代码不同仓库、不同评审流程，必然漂移 |
| 每个决策写一份完整设计文档 | 太重，会导致"因为麻烦所以不写" |

## 后果

**变好了**：

- 决策可追溯：任何人可以查到"为什么是块模型"以及当时考虑过什么；
- 评审有抓手：PR 里可以引用 ADR 编号，而不是重复论述；
- 新成员上手快：读一遍 `docs/adr/` 就理解了系统的关键取舍。

**变坏了 / 成本**：

- 每次架构决策多出一个文件的写作成本（这是刻意支付的）；
- 需要人维护"被取代"的状态，否则会出现互相矛盾的 ADR。

**后续要做的**：

- 每次阶段 Gate 评审时检查：本阶段是否有未记录的重大决策。

- **决策者**：<角色>

## 背景

## 决策
