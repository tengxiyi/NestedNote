# ADR-0001：修订内容用完整快照，而不是差量（delta）

- **状态**：已接受
- **日期**：2026-10
- **相关**：铁律 T1（数据不可丢）、T6（变更可追踪）、D1（原子写）、Q2（迁移不可改）、P2（先测量再优化）
- **背景文档**：`docs/design/06-SQLite数据库设计.md` §4.8、`docs/design/19-笔记本树右键菜单规划.md` §4.3

---

## 背景

"修订对比"被定为第一个创新项。但核对后发现一个前提不成立：

`revisions` 表**只存元数据**（`version` / `created_at_ms` / `device_id` / `operation` /
`parent_revision_id`），**没有任何内容列**。设计文档 §4.8 明确把它定位为
"追加型审计"，并把"含内容的版本历史"划到 P7。

也就是说：**没有内容可以对比**。这个功能不是"加一个 diff 界面"，
而是要先补一层数据。

于是产生本 ADR 要回答的问题：**修订内容怎么存？**

---

## 决策

**每个修订保存一份完整的文档快照**（序列化后的 JSON 字节），
存在新表 `revision_documents`；**不做差量压缩**。

```sql
CREATE TABLE revision_documents (
    revision_id BLOB PRIMARY KEY REFERENCES revisions (id),
    content     BLOB NOT NULL        -- 与 documents.content 同一序列化格式
);
```

写入时机：与 `revisions` 行**同一事务**创建（铁律 D1）。
读取方式：`LEFT JOIN`，**允许缺失**（迁移前的历史修订没有快照）。

---

## 备选方案与为什么不选

### 方案 A：完整快照（**选中**）

| 维度 | 评价 |
|---|---|
| 正确性 | **最高**。一条修订 = 一份完整内容，不存在"重放链条"出错的可能 |
| 实现复杂度 | 最低。写入就是再插一行，读取就是一个 JOIN |
| 崩溃/损坏影响 | 单条快照坏掉只影响那一条，其它修订完好 |
| 存储 | 最差。见下方测算 |
| 同步（P6） | 简单：快照是自包含的，可独立传输 |

### 方案 B：差量（delta）

存"相对上一版的差异"，读取时顺着 `parent_revision_id` 链重放。

- **为什么不选**：它把**读取**变成了有状态重放。任何一处链条断裂
  （父指针悬空、快照缺失、算法版本变更）都会让整条历史**不可读**，
  而且失败是"读到一半发现不对"这种最难处理的形式。
- 与铁律 T1 的精神冲突：为了省磁盘，把"能读出来"变成"要能重放对"。
- 而且它的收益依赖一个**我们还没测过的前提**：编辑是否真的产生大量小修订。
  按 P2（先测量再优化），在没有实测数据前引入这个复杂度是不合理的。

### 方案 C：只存"上一个版本"，不保留完整历史

- 做不了"与任意历史版本对比"，而这正是本功能的价值。
- 排除。

---

## 存储测算（真实数据，非估计）

在示例库上实测（`python` 直接读 SQLite）：

| 指标 | 实测值 |
|---|---|
| 笔记数 | 42 |
| 修订数 | 87 |
| 序列化后的文档平均大小 | 约 **375 字节** |
| 最大的文档 | **603 字节** |

按此推算几种规模（假设每次修订都存快照）：

| 场景 | 笔记数 | 每篇修订数 | 平均大小 | 快照总占用 |
|---|---|---|---|---|
| 轻度使用 | 100 | 20 | 2 KB | **约 4 MB** |
| 中度使用 | 500 | 50 | 2 KB | **约 50 MB** |
| 重度使用 | 2000 | 100 | 4 KB | **约 800 MB** |

**结论**：在"每次自动保存都产生一条修订"的前提下，重度使用会长到数百 MB 量级。

**但这个测算是保守的**，因为它假设了最坏情况。而且有两条天然的抑制因素：

1. `save_note` 已经只在**内容真的变化**时才产生修订（技术债 #11 已偿还）。
   编辑器有 1200ms 防抖，因此"敲一个字一条修订"不会发生；
2. 笔记彻底删除时，其修订与快照**一并删除**（`purge_*` 已覆盖
   `revisions` 表，新表随主表清理）。

**后续可优化项（不是现在做）**：
- 同样的内容去重（同一篇笔记连续两次保存内容相同 → 复用快照）。
  内容寻址的思路在这里同样适用；
- 修订保留策略（如"只保留最近 N 条 + 每天第一条"）；
- 真到了数百 MB，再按 P2 用真实数据重新评估是否引入 delta。

**本 ADR 明确接受**："先正确，再省空间"。若将来存储成为真实问题，
应当基于实测数据再开一条 ADR，而不是现在预防性地引入重放复杂度。

---

## 缺失快照的处理（重要）

迁移 `0003` 之前产生的修订**没有快照**。它们必须被如实处理：

- 代码里 `revision_documents` 是 `LEFT JOIN`，允许为 `NULL`；
- 界面显示"**此版本没有内容快照**"并说明原因（旧版本记录），
  **不显示空白 diff**——空白会让用户以为"这一版是空的"，
  从而怀疑数据损坏；
- **不做**"用当前内容回填历史快照"：那是在伪造历史。
  审计材料一旦被补写，就不再是审计材料。

---

## 影响

- 新增迁移 `0003_revision_documents.sql`（`0001`/`0002` 不可修改：铁律 Q2）
- `repositories/revisions.rs` 增加快照的写入与读取
- `save_note` / `create_note` 在写修订的同一事务里写快照
- 新增 diff 能力（内核 + FFI + 界面）
- 同步协议（P6）需要带上快照字节；届时评估是否改为按需拉取

## 未决问题（明确留待后续）

1. **修订密度**：是否要给修订加"最小间隔"（如 5 分钟），
   让历史变成"有意义的节点"而不是"每次自动保存"？
   这会影响 diff 的可读性，但有测试覆盖"无变更不产生修订"，
   独立于本 ADR，可单独决策。
2. **是否需要保留策略**（自动清理旧修订）。当前**没有**，
   因此修订会一直增长到笔记被彻底删除为止。
