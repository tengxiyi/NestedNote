# ADR 0002 —— 富文本编辑面选型（R2）

> 状态：**建议，待用户确认**
> 背景：R1 富显示已交付（`docs/design/09-编辑器技术方案.md`）。
> R2 要回答的问题是：用户**在哪里、以什么方式**编辑块与行内标记。
> 本 ADR 给出三个选项、权衡与建议。确认后 09 方案 §5 的其余问题
> （选区/撤销语义、表格图片编辑）按所选路线细化。

---

## 选项 A：引入第三方编辑器框架

**候选**：`super_editor`（MIT）、`appflowy_editor`（AGPL-3.0，与本项目
同许可，可用）、`fleather`（MIT，Quill/ delta 模型）。

**优点**

- 光标、选区、撤销重做、中文 IME 这些"编辑器的硬骨头"有现成实现；
- 真正的所见即所得，与印象笔记的体验差距一次性拉平。

**缺点与风险**

- **文档模型不匹配**：三方都自带 Document 模型，需要"我们的 Block serde
  ↔ 三方模型"双向映射层。映射是永久维护成本：上游每次 API 变化都要跟；
- 依赖健康度被绑：编辑器是应用的核心，框架停更/大改 = 最高级别的风险；
- IME 成熟度不一：super_editor 对中文输入做过大量修复，但仍偶发回归；
  出问题时我们排查的是别人的代码。

## 选项 B：渐进增强（保持系统文本框，行内标记走 Markdown 语法）

**做法**：编辑面仍是纯文本 `TextField`（系统输入法、单框撤销全部保留），
新增对行内标记的**语法支持**：`**粗体**`、`*斜体*`、`~~删除线~~`、
`` `行内代码` ``、`[文本](地址)`。扩展 `text_projection`：

- 解析：Markdown 行内语法 → `InlineMark`（字节偏移在解析时自然得出）；
- 序列化：marks 渲染回 `**…**` 等形态（往返可逆）；
- R1 预览渲染行内样式 → **"编辑写标记，预览见真容"**；
- 格式菜单加"粗体/斜体"项，等价于手工敲 `**`。

**优点**

- **零新依赖、零迁移**；中文 IME 零风险（仍是系统输入框）；
- 失败模式最小：这一步失败只损失一个功能，不动摇编辑器本体；
- 与既有资产完全咬合：无损投影、预览渲染、格式菜单都是现成的；
- 存储契约（块 + 偏移标记）与 Markdown 天然亲和。

**缺点**

- **不是所见即所得**：编辑时看到的是标记语法，样式要到预览态才呈现；
  与印象笔记的体验差距仍存在（只是缩小）；
- 用户需要接受"Markdown 风格"的心智（对本地笔记用户接受度高，
  对纯印象笔记迁移用户是一次习惯迁移）。

## 选项 C：自研完整块编辑器（每块一个编辑 widget，自管光标/选区/撤销）

**优点**：体验上限最高，模型完全自主。
**缺点**：工作量与风险均为全项目之最；光标跨块、IME 组合期、
撤销栈都是深水区。**不建议现在做**；若 B 验证后确有强需求再立项。

---

## 建议：先 B 后 C

1. **R2 首版选 B**：行内标记语法 + 预览渲染 + 格式菜单入口。
   交付快、风险小，且与"标记 → 块"的既有管线一致；
2. B 上线后观察真实使用反馈；若"非所见即所得"成为高频痛点，
   再以 **A（appflowy_editor，AGPL 兼容）** 为候选做第二次 ADR——
   那时我们已经用 B 把行内标记的**存储与渲染**打磨完，
   换编辑面只换输入方式，迁移成本远低于现在直接上 A；
3. C 永远保留为"体验上限"路线，不预设时间表。

## 对确认的要求

需要用户回答一个问题：**"编辑时看到 `**加粗**` 这样的标记、
预览里才变样式"，可以接受吗？**

- 可以 → 选 B，本 ADR 转"已接受"，进入实施；
- 不可以（必须所见即所得）→ 转 A，需接受映射层的长期维护成本，
  且 R2 工期按 A 重新估算。
