# ADR 0003：迁移文件哈希护栏

- **状态**：已接受
- **日期**：项目 P0 阶段
- **决策者**：项目负责人
- **相关**：铁律 Q1/Q2/Q10、`client/crates/nested-db/tests/migration_guard.rs`

## 背景

数据库迁移文件一旦发布给用户，就**再也不能修改**：老用户的库已经按旧文件迁移过，
永远不会重新执行它；新用户的库却按新文件创建。两者 `user_version` 相同、
实际结构不同——这类问题不会在开发期暴露，只会在生产环境的某个用户机器上爆雷。

"不要改历史迁移"是一条口头约定，而口头约定在赶工时必然失效。
需要把它变成**机器强制**的规则。

## 决策

在 `client/crates/nested-db/tests/migration_guard.rs` 中实现四道护栏：

1. **哈希清单**：测试内硬编码每个迁移文件的 SHA-256。任何字符改动都会失败。
2. **清单一致性**：磁盘上的 `.sql` 文件必须与代码内嵌的 `MIGRATIONS` 数组一一对应
   （数量、名称、内容全等）。
3. **命名规范**：迁移名称必须以 `NNNN_` 开头并与版本号对应。
4. **行尾规范**：迁移文件不得含 `CR`。

配套措施：

- 迁移 SQL 通过 `include_str!` 编译期内嵌，避免"运行时找不到文件"；
- `.gitattributes` 强制迁移文件为 LF（否则同一份文件在不同平台哈希不同，
  护栏会误报"被篡改"）；
- `scripts/normalize-line-endings.ps1` 提供一键修复，CI 有独立的 `line-endings` 作业。

## 备选方案

| 方案 | 优点 | 为什么不选 |
|---|---|---|
| 只靠 Code Review 与文档约定 | 零成本 | 赶工时必然失效；且 review 者很难发现"这个 SQL 被改了一个字符" |
| 用成熟的迁移框架（如 refinery / sqlx migrate） | 功能完整，自带校验和 | 客户端要求 SQLite + 极简依赖（铁律 A8）；且我们需要与"多端一致"绑定得更紧的语义。用 SQLx 会给客户端引入 tokio 生态 |
| 哈希存进数据库而非测试代码 | 无需改代码 | 数据库里的哈希本身也可能被改；且新装用户没有历史记录可比对 |
| 只用 CI 脚本检查哈希 | 不入编译流程 | 开发者本地 `cargo test` 时无感知，问题推到 CI 才暴露 |

## 后果

**变好了**：

- "不得修改历史迁移"从约定变成编译/测试级强制，且**本地就能发现**；
- 行尾漂移（Windows 常见）这一类误报有明确的修复路径，不会演变成"关掉这个测试"；
- 迁移内容被内嵌进二进制，发布产物不依赖外部 SQL 文件的部署正确性。

**变坏了 / 成本**：

- 新增迁移时必须手工更新哈希清单（刻意保留：强制作者意识到"这是一次发布"）；
- 若某条迁移从未发布给任何用户却写错了，修正它需要走 ADR 并更新哈希
  （这是有意的摩擦，避免"随手改历史"）。

**后续要做的**：

- P1 阶段补齐"从上一版本库升级到最新"的端到端迁移测试（当前只有护栏，没有升级路径测试）；
- 服务端 PostgreSQL 迁移同样需要护栏（`server/migrations/`），P6 落地。
