# ADR 0004：铁律自动检查器用 Rust 实现

- **状态**：已接受
- **日期**：项目 P0 阶段
- **决策者**：项目负责人
- **相关**：铁律附 A（规则 × 门禁对照表）、`client/tools/nested-rules`

## 背景

《工程铁律》附 A 要求"每一项都应对应一条可执行命令"。最初的实现是
`scripts/check-rules.ps1`，在 P0 落地时遇到两个具体问题：

1. **编码**：Windows PowerShell 5.1 会把无 BOM 的 UTF-8 脚本按 ANSI(GBK) 解码，
   脚本里的中文直接乱码，甚至触发解析错误（`字符串缺少终止符`）。
   解决办法是把所有输出改成 ASCII——可以，但这意味着脚本永远不能有中文提示，
   而项目其余部分都是中文注释。
2. **可调试性**：脚本抛出 `ParameterBindingValidationException` 时，
   错误位置只报告到"脚本第几行"，`$_.InvocationInfo` 给不出出错的具体 cmdlet
   与实参，排查一个 `null` 路径花了几轮往返仍未定位。

门禁工具的价值完全取决于**它自己是否可靠**：一个经常误报或难以调试的检查器，
最终会被 `continue-on-error` 或本地跳过绕过，于是等于没有。

## 决策

把规则检查器改写为 Rust 二进制 `client/tools/nested-rules`：

- **零第三方依赖**（仅标准库）：门禁不应成为 CI 中最脆弱的一环；
- **lib + bin 结构**：检查逻辑在 lib 中，每条规则都有单元测试（22 个）；
- **只查产品代码**：只扫 `src/`，且跳过 `#[cfg(test)]` 模块——
  测试里 `expect()` 是正确做法；
- **宁可漏报不可误报**，并在附 A 中**诚实记录检查盲区**；
- `scripts/check-rules.ps1` 保留为本地快捷包装（转调该二进制），
  这样未来换实现只需改一处。

判定策略刻意保守，例如：

- Q4 只拦截"`format!` + SQL 关键字 + 小写插值占位符"，`{COLUMNS}` 这类常量放行；
- D2 允许 `note_tags` / `note_attachments` 这类纯关联表的物理删除；
- S3 用"敏感字段名 + 引号内 ≥ 8 字符"的启发式，并放行标注 example/placeholder 的值。

## 备选方案

| 方案 | 优点 | 为什么不选 |
|---|---|---|
| 继续用 PowerShell，输出全 ASCII | 无新代码 | 编码限制永久化；错误定位问题未解决；无法单元测试 |
| 用 Python 脚本 | 跨平台、字符串处理方便 | 引入第二种工具链（CI 与开发机都要装），而仓库已经是 Rust 项目 |
| 全部交给 clippy / cargo-deny 等现成工具 | 生态成熟 | 无法表达项目特有规则（软删除、两端隔离、迁移哈希）；且 `expect_used` 在测试里必然误报，clippy 无法按"产品代码 vs 测试"区分 |
| 只写文档，靠 Review | 零成本 | 与"附 A 要求可执行"冲突；实测人在赶工时不会逐条自查 |

## 后果

**变好了**：

- 检查器跨平台、可测试、与文件编码无关；
- 违规信息可执行：文件、行号、违反哪条铁律、**怎么改**；
- 本地与 CI 用同一个权威实现，结果一致；
- 每条规则的判定逻辑有测试覆盖，改规则时不会悄悄放宽。

**变坏了 / 成本**：

- 检查器本身成为需要维护的代码（约 700 行）；
- 保守策略意味着**已知会漏报**（例如 SQL 用 `String` 拼接、凭据拆分拼装）——
  这些盲区已写入铁律附 A，由 Review 兜底。

**后续要做的**：

- Flutter 代码落地后，补充 Dart 侧的分层检查（UI 不得直接访问存储）；
- 把"非法 `#[allow(clippy::...)]` 未附理由"也纳入检查；
- 覆盖率阈值（铁律 Z1）接入 CI 后，把它也变成一条规则。
