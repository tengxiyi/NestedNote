# 09 · 编辑器技术方案

> 状态：✅ 已完成（2026-10，R1 富显示的设计与实现依据）
> 前置：用户在菜单栏规划时把富文本搁置（"在做富文本之前，先补齐菜单栏以及功能"），
> M1–M3 完成后按用户确认的分期提上来。**先显示（R1），后编辑（R2）。**

---

## 0. 问题与目标

存储层是完整的块模型（P0 契约 A10：只加变体不改语义），但编辑器自 P1 起是
**纯文本投影**。后果：

- 附件显示为 `[file: 名](id)` 标记（用户实际遇到并指出）；
- 标题/列表/代码块/引用/待办没有视觉差异；
- 打印/PDF、内链、导出行内样式都被卡住。

目标：把块模型**渲染**出来，再（第二步）让用户**直接编辑块**。

## 1. 两层拆分

| 层 | 内容 | 状态 |
|---|---|---|
| **R1 富显示** | 块 → 真正的可视组件（只读） | 本文实现 |
| **R2 富编辑** | 在块上编辑 + 行内标记（加粗/斜体/…） | 待 ADR（见 §5） |

拆分的理由：渲染层一次解锁附件预览、打印/PDF 渲染基础、内链预览、
导出保真；编辑面是全项目最大的单项工程（Flutter 无现成块编辑器），
混在一起会把"看得见"的好处推迟数倍。

## 2. R1 设计

### 2.1 数据通路（内核是唯一事实来源）

```
SQLite revision_documents / notes.document
  → nested-core get_note_document()          （与存储同源的 serde 结构）
  → serde_json 序列化                        （与落库字节同一套定义）
  → FFI notes_read_document() → document_json
  → Dart core 层解析为 UiBlock 列表          （lib/core/blocks.dart）
  → app 层 DocumentView 渲染                 （lib/app/document_view.dart）
```

关键决策：

- **JSON 而不是 FRB 镜像枚举**：`Block` 的 serde JSON（`tag = "type"`，
  snake_case）就是**落库的字节格式**。Dart 渲染它 = 渲染真正存储的东西。
  走 FRB 镜像枚举要么把结构搬到契约面（重复定义），要么遇到 opaque 问题
  （`MaintenanceResult`/`ActivityEntry` 都踩过）。
- **解析放 core 层**（A-LAYERING）：app 只认 `UiBlock`，不认 JSON 与绑定。
- **event 中间层不引入**：预览读取走与 `notes_read` 同一个 get_note_document。

### 2.2 双模式切换

编辑器工具栏加「预览/编辑」切换。进入预览前**先保存当前编辑**
（复用既有 `_save`），否则预览的是旧内容；切换回来即回到文本编辑器。
纯文本编辑器继续作为**编辑面**存在——R1 不动编辑行为，零迁移风险
（M2 的无损投影保证两种视图看到同一份数据）。

### 2.3 渲染规则（首版）

| 块 | 渲染 |
|---|---|
| Paragraph | 正文文本 |
| Heading(1–6) | 标题层级字号（headlineSmall → labelLarge 递减） |
| BulletList / OrderedList | 项目符号 / 编号列表 |
| Checklist | 勾选框（只读显示勾选态）+ 文本 |
| Quote | 左侧竖线 + 缩进 |
| Code | 等宽字体 + 浅底色容器，语言标注 |
| Divider | Divider |
| Image | 读取附件字节渲染（按 id 内容寻址），加载失败显示替代文本 |
| File | 附件卡片（文件名），点击打开附件面板可另存 |
| Table | 表格行（首行表头加粗） |
| Link | 带下划线的文本 + 地址小字（点按复制地址——不引 url_launcher） |

### 2.4 已知边界（有意不做，R1 内明确）

- **行内标记被忽略**（加粗/斜体等）：它们是字节偏移，显示层按纯文本渲染。
  编辑器目前也产生不了行内标记，故无真实数据受损；R2 落地时一并处理。
- **表格简化渲染**：无合并单元格/列宽，逐行文本。
- **不打开外部 URL**：需要 `url_launcher` 依赖与安全策略（外链确认），
  单独决策，不做隐式放行。

## 3. 与纯文本编辑器的关系

- 数据层唯一：两种视图都来自 `get_note_document`；
  文本编辑器读 `document_to_text` 投影，预览读同一 Document 的 JSON。
- M2 的无损往返保证：文本编辑器保存的块，预览渲染一致；
  反过来预览态不产生编辑，不引入新写路径。
- 格式菜单产生的标记（`# `/`- `/```` ``` ````）在预览里呈现为真实块——
  这就是"标记 → 块"管线的可视化验证。

## 4. 测试策略

- Rust：`notes_read_document` 返回的 JSON 含正确的块类型（回归防线）。
- Dart core：JSON → UiBlock 解析（含 checklist/file/divider/未知类型容错）。
- Dart app：DocumentView 渲染冒烟（标题/列表/代码/附件卡出现）。

## 5. R2 待决问题（ADR 清单，实施前必须回答）

1. **编辑面选型**：自研块编辑面 vs 引入第三方（如 super_editor / appflowy_editor）。
   评估维度：中文输入法（IME）兼容性、撤销/重做跨块语义、依赖健康度、许可。
2. **行内标记的写路径**：扩展文本投影（标记的文本表示）还是绕开文本层直写块。
   前者保双模式共存，后者是 R2 的自然终点。
3. **选区与撤销跨块语义**：Flutter `TextField` 的撤销是单框的，
   块间撤销需要自管历史。
4. **表格与图片的编辑体验**：R2 首版是否只读保留（推荐：是）。

## 6. 明确不做（本期）

- 移动端/Web 适配（仍是 Windows 桌面优先）
- 协同编辑、冲突合并（同步阶段的设计）
- 打印/PDF（R1 渲染层就绪后单独立项）
