# 笔记本树右键菜单 —— 功能规划

> 状态：**待确认**（确认后才开始实现）
> 输入：用户提供的 4 张印象笔记右键菜单截图
> 核对基线：内核公开 API 清单（`client/crates/nested-core/src/api.rs`）、迁移文件（`0001`/`0002`）

## 0. 先把层级讲清楚

印象笔记的侧栏是**三层**，每层右键菜单差异很大。截图核对如下：

```text
笔记本（root，不是一个可操作对象，只是分组标题）
└── 笔记本组（stack）        ← 截图 3 的菜单：12 个动作（最全）
    └── 笔记本（notebook）   ← 截图 4 的菜单：18 个动作
        └── 笔记             ← （未截图，但已有"新建笔记/打开笔记"等）
```

证据：

| 截图 | 目标 | 菜单里的关键证据 |
|---|---|---|
| 3 | 笔记本组（"个人信息"） | 有「**在"个人信息"中创建笔记本**」「移出笔记本组(M)」——说明它是"装着笔记本的组" |
| 2 | 笔记本组，且在组内 | 有「在"个人信息"中创建笔记本...」「**重命名/删除**」 |
| 4 | 笔记本（"60天挑战"，带计数 2） | 有「**新建笔记(N)**」「**添加标签(T)**」「**删除笔记(E)**」——说明它直接装笔记 |

⚠ **一处与我们要做的创新直接冲突**：截图 4 有「删除笔记(E)」。印象笔记的这个动作把笔记移入它自己的回收站；但我们**没有"笔记本回收站"**，
所以我们的同位置动作应该是「**移入回收站**」，而且**绝不做"彻底删除"**——见 §4 的 T1/T7 说明。

## 2. 按「实现依赖」重新分组

上面的清单是**按印象笔记的分类**列的。要排实现顺序，得**按我们缺什么**重列一次——同一类依赖的放一起做，避免反复进同一块内核代码。

### A 类：内核已就绪，只差接线（真·UI 活）

可以直接开工，不动内核：

1. **重命名笔记本**（F2 快捷键 + 右键）——内核 `rename_notebook` 已存在且已测
2. **在任意层级新建**笔记本 / 子笔记本
3. **移入回收站**（笔记本与笔记，统一文案）
4. **属性**对话框（名称、id、父级、创建/更新时间、笔记数、子树笔记数）
5. **查找/过滤笔记本**（本地过滤，不需 FTS5）
6. **快捷方式**（左栏顶部区，本地表 `shortcuts`）
7. **新建笔记并直接打开**（笔记本层级右键）
8. **移动到笔记本**（笔记已有；复用中栏那个对话框）

**产出**：右键菜单 + F2 + 属性框 + 过滤框。**这是可独立交付的第一批。**

### B 类：需要补内核（小改动，但要动数据库/API）

9. **移动笔记本**（改 `parent_id`）——必须**检测环**：不能把祖先移到自己的后代里，
   否则树会出现自引用环、遍历直接死循环。这是 B 类里**唯一有正确性风险**的一项，要写测试。
10. **给笔记设置标签**（整体替换语义：`set_note_tags(note_id, tags)`）
    —— 关联表已有，缺一个"设置"入口与"标签软删后可复用同名"（技术债 #13）
11. **笔记深拷贝**（"复制笔记 / 创建副本"）：
    复制 `documents` 行 + 复制 `note_tags` 关联；**附件只复制引用不复制字节**
    （内容寻址的收益：同一份内容天然去重，见铁律 T8）
12. **笔记本深拷贝**（"复制笔记本"）：遍历子树，对每个笔记本做 #11

> 注：#10 的"标签同名复用"是**已登记的技术债 #13**，本来就该修，正好一起。

### C 类：需要新能力（渲染层）

13. **导出**（Markdown → HTML → 整库 JSON）：
    这是**块模型落地以来第一个真正的消费者**，也是**独立于菜单**的一块活。
    建议单独排期，不要在菜单里赶。

    为什么不能"顺手做"：导出质量取决于块模型 → Markdown 的映射细节
    （行内标记嵌套、列表层级、代码块语言、表格、附件路径），
    而当前**编辑器根本不产生**这些块（右栏是纯文本两阶段）。
    也就是说：**导出会先于编辑器成熟**，得接受"导出的保真度暂时无处验证"。

### D 类：创新项（本项目独有，印象笔记没有）

见 §4。

## 3. 建议的实施顺序

每一步都能**独立验收**，且不阻塞后一步。

| 步骤 | 内容 | 依赖 | 可验收标准 |
|---|---|---|---|
| **S1** | 三个层级的右键菜单骨架 + A 类全部 | 无 | 菜单项都能点、都有反应；F2 可重命名；属性框显示正确计数 |
| **S2** | B 类内核补全（移动笔记本 / 标签设置 / 深拷贝） | S1 | 移动笔记本的**环检测**有测试；深拷贝后附件去重（磁盘不增长） |
| **S3** | C 类导出（Markdown 先行） | S2 | 导出的 .md 能重新导入且文本不丢 |
| **S4** | D 类创新项，按 §4 的优先级 | S1 | 各自独立 |

**为什么 S1 排第一**：它是唯一一批「零内核改动、零数据库迁移」的活，
风险最低、能最快看到完整效果，而且**能立刻验证菜单结构是否符合你的预期**——
如果层级划分不对，改结构的成本在 S1 最低。

## 4. 明确不做的项，以及为什么

### 4.1 ⛔ 添加隐私锁（印象笔记 #10）

这不是"没时间做"，而是**我不应该在没有你确认的前提下做**：

- 它有加密方案选择（SQLCipher 全库加密 / 只加密敏感字段 / 只是 UI 锁屏）
- **"只是 UI 锁屏"是危险的假安全**：文件还在磁盘上明文躺着，
  用户会以为"锁住了"。这比不做更糟——它给人错误的安全感。
- 真正的加密要改存储层（SQLCipher 或字段级），并引入密钥管理
  （密钥存哪里？忘记密码怎么办？），是一个**独立的设计决策**。

**建议**：单独立项 + 先写 ADR。`nested-crypto` crate 目前只有 trait 占位，
说明当初就是打算"方案定了再实现"（见技术债登记）。
**在你确认加密方案之前，我不做这个菜单项，也不放一个灰色占位按钮**
（放了会让人以为"以后会有"，而实际可能是永远不做）。

### 4.2 ⛔ 共享 / 演示 / 便签 / 思维导图 / 保存查看设置

| 项 | 不做的理由 |
|---|---|
| 共享笔记本 | 需要账号体系 + 服务端权限模型。我们的同步是"设备间同步自己的数据"，不是"多用户协作"（协作在技术文档里是 P3 CRDT 阶段） |
| 演示 | 需要全屏演示态与分页逻辑，是独立功能 |
| 设为桌面便签 | 需要常驻置顶窗口与托盘，是独立子系统 |
| 思维导图目录 | 与本产品"块模型 + 内容寻址"的定位无关；而且它导出的是印象笔记自有格式 |
| 保存查看设置 | 我们**用"智能视图"替代**（见 4.3），比"保存列宽/排序"更有用 |
| 样式 | 纯 UI 噪音，我们的主题已由 Material 3 统一 |

### 4.3 🔶 创新项（建议做，这是差异化所在）

印象笔记的「创建任务」「保存查看设置」我不照抄，因为它俩是为**它的**产品形态服务的。
换成对我们用户真正有用的：

| 创新项 | 替代印象笔记的 | 实现代价 | 为什么值得 |
|---|---|---|---|
| **智能视图** | 保存查看设置 | 中（存筛选条件 + 迁移一条表） | 把「保存列宽」升级成「保存查询」：如"所有未打标签的笔记""本周更新过的" |
| **批量操作**（多选后右键） | 无 | 中 | 真实痛点：整理几十篇笔记时逐个移动很痛苦 |
| **修订对比** | 无 | 中（`revisions` 表已有） | **我们已有修订历史却只显示列表**——把"看到历史"升级成"看清改了什么"。这是自研相对印象笔记的实打实优势 |
| **反向链接 / 内链** | 复制笔记链接 | 中高（需链接表 + 引用扫描） | 笔记之间的关联是笔记软件的核心价值；且与"嵌套"的产品名呼应 |
| **去核对 / 去扩写 / 去回顾** | 创建任务 | 低（纯 UI 引导） | 不引入任务模型，但给用户**离开电脑后的动作**。避免了"半个任务系统"这种最糟的中间态 |
| **置顶笔记** | 无 | 低 | `notes.updated_at_ms` 排序之外的一个常用诉求 |

**关于 AI**：技术文档把 AI 排在 **P2**，而且需要决定用本地还是云端模型。
我不建议现在做，也不建议用"AI 帮我写"这种按钮占位——
**在能力没落地前放按钮，是在教用户不信任界面**。

### 4.4 一个必须先说清的取舍：「复制笔记链接」在单机应用里没有意义

印象笔记的「复制笔记链接」生成的是**服务端 URL**（`https://...`），因为它是云应用。
我们是**本地优先**（铁律 T3），没有服务端 URL 可复制。

所以这一项要么：
- **(a) 不做**（老实说"本地应用没有链接可复制"）
- **(b) 做成真正的内链**：`nested://note/<id>`，并支持在笔记里引用其它笔记 + 反向链接面板

我推荐 **(b)**，但它是 §4.3 里代价最高的一项，而且**必须先有富文本编辑器**
（否则用户没法在正文里插入链接）。建议排在 S4 最后。

## 5. 三个层级的菜单设计（建议稿）

考虑我们的"软删 + 无硬删"约束，菜单比印象笔记短，但每一项都真的能用。
**灰色不可点比"点了没反应"更诚实**，所以我删掉了做不到的项，而不是留占位。

### 5.1 笔记本组（stack）右键

```text
在"X"中创建笔记本…

```

```text

─────────────────────

─────────────────────
移动到…
添加到快捷方式
─────────────────────

复制笔记到…
─────────────────────
属性
```

### 5.3 笔记（中栏列表项）右键 —— 补全已有的长按菜单

```text
打开
─────────────────────
移动到…                   Alt+Shift+M
置顶 / 取消置顶             ← 创新
复制一份                   ← B 类深拷贝
─────────────────────
添加标签…

─────────────────────
```

> **注意**：三层菜单里我都**没有**放"彻底删除"。
> 依据铁律 **T1（数据永不丢失）** 与 **T7（软删除）**：
> 全库实体表没有任何 `DELETE FROM`（只有关联表有，那是关系不是实体）。
> 印象笔记的「删除笔记」进它自己的回收站，我们的对应动作就是「移入回收站」。
> 如果你想要"彻底删除"（比如为隐私），那是一个**独立决策**：
> 它需要"二次确认 + 明示不可恢复 + 可能需要先做加密"，
> 我不会顺手加进去。
