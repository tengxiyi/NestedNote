# 20 · 菜单栏与功能补齐规划

> 状态：**待确认**
> 依据：用户提供的 8 张印象笔记菜单截图（文件 / 编辑 / 查看 / 笔记 / 格式 / 工具 / 帮助）
> 前置：本规划**先规划不写码**。确认后按阶段实施。

---

## 0. 这份规划要解决的问题

用户的原话：

> 在做富文本之前，我们来补齐菜单栏以及功能。我把印象笔记的截图给你，
> 参照它做我们的版本。不一定要完全照搬，根据我们软件的特点，
> 选择性参照做一部分，然后再做一些我们特色的。先规划

因此本文回答四个问题：

1. 我们的菜单栏**长什么样**（结构与分组）
2. 印象笔记的每一项，我们**做 / 不做 / 换个做法**
3. 分几个阶段，每阶段交付什么
4. 我们**自己的特色**放在哪里

## 0.1 铁律约束（决定了取舍的边界）

| 约束 | 影响 |
|---|---|
| **F5 禁止假按钮**（用户明确要求：不要"画好但点不动"的项） | 凡是没有真实实现的项，**不放菜单**，而不是放上去置灰。这直接决定了阶段划分：菜单项必须与能力同步交付 |
| T4 内核是唯一事实来源 | 能做成菜单项的功能，其业务规则必须在 `nested-core`，界面只调用 |
| E2/E3 错误要能指导用户 | 菜单项失败时给"下一步怎么办"，而不是泛化提示 |
| T7 软删除 | "删除"一律进回收站；彻底删除只在回收站 |
| T1/T6 数据不丢 + 修订 | 任何破坏性操作都必须可恢复或有修订兜底 |

## 1. 菜单栏结构

七项与印象笔记对齐（用户已熟悉的肌肉记忆），但**内容按我们的能力裁剪**：

```
文件(F)  编辑(E)  查看(V)  笔记(N)  格式(O)  工具(T)  帮助(H)
```

### 与印象笔记的结构性差异

| 差异 | 理由 |
|---|---|
| **不设"笔记(N)"里的"共享/演示/打印"** | 我们没有同步服务、没有演示模式、打印对笔记应用不是核心 |
| **"格式"菜单先是小的** | 富文本尚未实现。第一阶段只放**块级操作**（标题/列表/引用/代码/分隔线），这些在块模型里**已经支持**，只是编辑器还没暴露 |
| **"工具"不含密码锁** | 用户在 P1 明确说过"暂时不考虑" |
| **多一个"标签"顶层入口**（放在"笔记"下不如放"查看"） | 我们没有印象笔记的标签树侧栏；标签目前只在右键菜单里，缺乏全局入口 |

## 2. 能力矩阵：逐项处置

图例：✅ 内核已支持，只是没接界面 ｜ 🔨 需要新实现 ｜ ⏭️ 本期不做 ｜ 🚫 不建议做

### 2.1 文件(F)

| 印象笔记项 | 我们的处置 | 依据 |
|---|---|---|
| 新建笔记 | ✅ **做**（Ctrl+N） | 已有 |
| 新建笔记本 | ✅ **做** | 已有 |
| 新建子笔记本 | ✅ **做**（比印象笔记多这一层） | 我们的核心差异就是多层目录 |
| 新建标签 | ✅ **做** | 已有 |
| 新建群聊 / 新建本地笔记本 | 🚫 不做 | 无对应能力；本地笔记本在"本地优先"架构下是**全部**笔记本 |
| 新建已保存搜索条件 | ⏭️ 延后 | 依赖搜索（`nested-search` 是占位） |
| 导入 | ⏭️ 延后 | `nested-import` 是占位；且导入格式需要单独 ADR |
| 导出 | ⏭️ 延后 | 见 §5 的单独说明 |
| 附加文件 | 🔨 **做** | 内核有 `attach_file_to_note`，**界面完全没有入口**——这是真实能力浪费 |
| 保存附件 | 🔨 **做**（把附件另存到磁盘） | 内核有 `read_attachment`，缺界面 |
| 打印 / 另存为 PDF / 打印预览 / 页面设置 | ⏭️ 延后 | 依赖渲染层；PDF 还需要字体嵌入决策 |
| 账户 / 退出登录 | 🚫 不做 | 无账户体系（本地优先） |
| 退出 | 🔨 **做** | 目前只能点窗口关闭按钮 |
| **设置 / 偏好** | 🔨 **做**（我们自己的分组） | 数据目录、附件 GC、危险操作（核对完整性）——`check_integrity` / `gc_attachments` 内核已有 |

### 2.2 编辑(E)

| 印象笔记项 | 我们的处置 | 依据 |
|---|---|---|
| 撤销 / 重做 | 🔨 **做**（Ctrl+Z / Ctrl+Y） | **当前是缺口**：Flutter 的 `TextField` 自带有限的撤销，但跨"标题/正文两个框"不一致，且没有菜单入口。需要显式接 `UndoHistory` |
| 剪切 / 复制 / 粘贴 | ✅ **做**（放菜单，走系统剪贴板） | 文本框原生支持，菜单只是补入口 |
| 粘贴并匹配样式 | ⏭️ 延后 | 纯文本编辑器下无意义；富文本后再做 |
| 删除 | ✅ **做**（进回收站） | 已有 |
| 全选 | 🔨 **做** | 需要区分"全选正文"与"全选列表"——**我们特色的分离** |
| 查找和替换 | ⏭️ 延后 | 依赖搜索能力；且替换对块模型要处理"跨块匹配" |

### 2.3 查看(V)

| 印象笔记项 | 我们的处置 | 依据 |
|---|---|---|
| 左侧边栏 | ✅ **做**（已有，补菜单入口与快捷键 F10） | 已有折叠按钮 |
| 笔记列表 | 🔨 **做**（F11） | 目前不可折叠；三栏布局里"只看正文"是真实需求 |
| 笔记编辑界面 | 🔨 **做**（Ctrl+F11） | 同上，"只看列表"用于快速浏览 |
| 标签视图 | ⏭️ 延后到 P2 | 需要标签侧栏 |
| 快速搜索 | ⏭️ 延后 | 依赖搜索 |
| 共享给我 / 工作群聊 / 文件库 | 🚫 不做 | 无对应能力 |
| 搜索信息 / 编辑工具栏 / 状态栏 | 🔨 **部分做**：状态栏（词数、保存状态）**做**；搜索信息不做 | 状态栏是低成本的实用信息 |
| **缩放** | 🔨 **做**（编辑器字号，Ctrl+= / Ctrl+- / Ctrl+0） | 见 §4：我们做**字号缩放**而不是整体缩放 |

### 2.4 笔记(N)

| 印象笔记项 | 我们的处置 | 依据 |
|---|---|---|
| 在新窗口中打开 | ⏭️ 延后（**列为特色候选**） | 需要多窗口管理；我们目前单窗口三栏 |
| 演示 / 共享 / 复制笔记链接 | 🚫 不做 | 无同步服务；"链接"只有在有 URL 体系时才成立 |
| 复制笔记 | ✅ **做**（已有"复制一份"） | 已有 |
| 移动笔记 | ✅ **做**（已有） | 已有 |
| 创建笔记副本 | ✅ **做**（与"复制一份"合并，避免两个语义相同的项） | 已有 |
| 合并笔记 | 🔨 **做**（**特色**） | 块模型天然支持拼接；见 §4 |
| 标签 | ✅ **做**（已有标签编辑器） | 已有 |
| 删除笔记 | ✅ **做** | 已有 |
| 笔记历史 | ✅ **做**（**最大特色**） | 内核已有完整快照与 diff，界面只有只读对比。见 §4 |
| 字数和资源统计 | 🔨 **做**（**特色**：面向中文） | 见 §4 |

### 2.5 格式(O)

**第一阶段只做块级操作**——它们在块模型里已经存在，编辑器只是没暴露。

| 印象笔记项 | 我们的处置 | 依据 |
|---|---|---|
| 字体 / 字号 | ⏭️ 富文本阶段 | 需要行内标记编辑器 |
| 段落（对齐/缩进/行距） | ⏭️ 富文本阶段 | 块模型目前**没有**对齐/缩进字段 |
| 样式（标题/正文/引用/代码） | 🔨 **做** | `BlockKind` 已有 `Heading` / `Quote` / `Code` / `List` / `Checklist` / `Divider` |
| 插入表格 | ⏭️ 延后 | 表格编辑器成本高（`BlockKind::Table` 已有，但编辑体验要单独设计） |
| 插入水平线 | 🔨 **做** | `BlockKind::Divider` 已有 |
| 待办事项 | 🔨 **做** | `BlockKind::Checklist` 已有 |
| 超链接 | 🔨 **做**（**特色**） | `InlineMark::Link` 已有；内链是创新项之一 |
| 加密所选文本 | ⏭️ 延后 | `nested-crypto` 是占位，方案待 ADR |
| 简化格式 / 设为纯文本 | 🔨 **做**（两件事都需要） | "设为纯文本"是块模型的**回退出口**，很重要 |
| 缩放 | 🔨 **做**（见 §4） | |

### 2.6 工具(T)

| 印象笔记项 | 我们的处置 | 依据 |
|---|---|---|
| 同步 | ⏭️ 延后 | 服务端已有骨架，客户端同步引擎未接 |
| 密码锁 | ⏭️ 延后 | 用户明确说暂时不考虑 |
| 选项 | 🔨 **做**（与"文件 → 设置"合并，只留一处） | 避免两个入口指向同一件事 |
| 账户信息 | 🚫 不做 | 无账户 |
| 导入文件夹 | ⏭️ 延后 | 依赖导入 |
| 自定义工具栏 | 🚫 不做 | 收益低、状态管理复杂；我们的工具栏项本来就少 |

### 2.7 帮助(H)

| 印象笔记项 | 我们的处置 | 依据 |
|---|---|---|
| 帮助 / 入门指南 | ⏭️ 延后 | 需要内容与文档体系 |
| **快捷键(K)** | 🔨 **做** | 我们把快捷键集中在菜单栏，**必须有一处能查**。成本低、价值高 |
| 评价 / 升级 / 检查更新 / 更新说明 | ⏭️ 后做（更新检查需要发布通道） | 无发布通道 |
| 活动日志 | 🔨 **做**（**特色**） | 见 §4 |
| 关于 | 🔨 **做** | 版本号、构建时间、数据目录路径——排查问题时用户能直接念出来 |

## 3. 分阶段实施

阶段划分的原则：**每一阶段结束时，菜单里出现的每一项都能真的用**（铁律 F5）。

> ⚠️ 下面的"内核已有"是**实测核对过**的（`nested-core::NestedCore` 的
> 公开方法清单），不是凭印象写的。同时核对了 FFI 暴露情况——
> 有几项内核有、FFI 没有，**这会实实在在增加工作量**：
>
> | 能力 | 内核 | FFI | 结论 |
> |---|---|---|---|
> | `attach_file_to_note` | ✅ | ❌ | 需要补 FFI |
> | `read_attachment`（保存附件） | ✅ | ❌ | 需要补 FFI |
> | `gc_attachments`（附件 GC） | ✅ | ❌ | 需要补 FFI |
> | `check_integrity`（完整性核对） | ✅ | ❌ | 需要补 FFI |
> | `revision_snapshot` / `diff_revisions` | ✅ | ✅ | 直接可用 |
> | `duplicate_note` / `set_note_tags` | ✅ | ✅ | 直接可用 |
>
> 即：**M1 里"附加文件/保存附件"这两项不是纯界面工作**，各需要一条 FFI
> 加一层 Dart provider。规划时按"要写 Rust"估时间，别按"加个菜单项"估。

### 阶段 M1：菜单栏骨架 + 立刻可用的项

**交付**
- 顶部菜单栏（`MenuBar` + `SubmenuButton`），七项结构与快捷键标注
- 文件：新建笔记/子笔记本/标签、附加文件、保存附件、退出
  （**附加/保存附件需要补 2 条 FFI**）
- 编辑：撤销/重做（显式接 `UndoHistory`）、剪切/复制/粘贴、删除、全选（正文/列表分离）
- 查看：左栏 / 中栏 / 右栏三者的显示切换 + 快捷键
- 笔记：复制一份、移动、标签、删除、**笔记历史**（把已有对话框接到菜单）
- 帮助：快捷键一览、关于

**为什么这些放第一批**：多数是"内核已有 / 界面已有，只差入口"，改动集中、
风险低，且能立刻让菜单栏显得"真的是菜单栏"。

### 阶段 M2：实用补齐

- 格式菜单：块级操作（标题 1-3 / 列表 / 待办 / 引用 / 代码 / 分隔线）+ 设为纯文本
- 状态栏：字数、保存状态、当前目录
- 工具/设置对话框：数据目录、附件 GC、核对完整性、回收站保留期
  （**GC 与完整性核对需要补 2 条 FFI**）
- 查看：字号缩放

### 阶段 M3：特色功能

见 §4。

### 阶段 M4：延后项（逐项单独确认）

导出、打印、搜索、同步、加密、导入、标签侧栏、多窗口。

## 4. 我们的特色（不是照搬，是做印象笔记做不到或收费的）

排序依据：**内核已有的能力 × 用户真实痛点**。

### 特色 1：修订历史从"能看"到"能改" ⭐ 最高价值

现状：能看逐行 diff（`docs/adr/0001`）。

印象笔记把"笔记历史"放在**付费版**，且只能看不能回退。

我们做三件它做不到的：

1. **从任意版本恢复**——`revision_snapshot` 已有，恢复就是"用那一版的内容保存一次新修订"。
   注意**不是**回滚历史（那会破坏审计链），而是**新增一条修订**记录这次恢复。
2. **两版之间任意对比**——目前只与"上一版"比。改成可任选两个版本。
3. **恢复前预览差异**——"恢复这一版会丢掉什么"必须先看见。

**风险**：恢复是破坏性操作，必须二次确认 + 明确写出"当前版本会先存为一条修订，之后仍可找回"。

### 特色 2：面向中文的字数统计

印象笔记只给"字数"，而中文语境下真正有用的是：

| 指标 | 为什么有用 |
|---|---|
| **字符数（含/不含空格）** | 中文写作的实际计量单位 |
| 段落数 / 块数 | 体现结构规模 |
| 预估阅读时长 | 按 300 字/分钟（中文）算 |
| 创建 / 最后修改 / 修订次数 | 写作过程回顾 |

放在"笔记 → 字数和资源统计"，也可常驻状态栏。

### 特色 3：合并笔记（块模型的红利）

印象笔记的"合并笔记"会把几篇拼成一篇**且不可逆**。

我们做：
- 按在中栏的选中顺序拼接，每篇前插入**分隔线 + 原标题**
- 合并**前**显示将要产生的结构（哪些块、总字数）
- 合并后**原笔记不删**（进回收站由用户决定）——因为可逆比省一次点击重要
- 合并本身产生一条修订，可 diff 回看

### 特色 4：活动日志

记录"这个应用对我的数据做了什么"：何时清理了回收站、何时 GC 了附件、何时恢复了修订。
印象笔记的"活动日志"是给客服排查用的；我们做成**用户能看懂的本地变更记录**。

理由：自动清理是全项目唯一"用户没操作、数据却消失"的路径（T1 的例外），
必须**可追溯**——这本来就是 T1 修订说明里承诺的三重防御之一。

### 特色 5：内链与反向链接（复用 `InlineMark::Link`）

块模型已支持链接标记。做内部链接（`nested://note/<id>`）后，
"哪篇笔记提到了我"是图谱类应用的核心价值，而印象笔记没有。

**降级为阶段 M3 的可选项**：它需要链接的渲染、悬浮预览、失效链接处理，
比前四个重。若时间有限可后置。

## 5. 关于"导出"：需要单独确认

导出被放在"文件"菜单里，但它是**整块新能力**，不应混在菜单栏阶段里悄悄做掉。

现状（需用户知悉）：`nested-export` 是占位 crate；且**当前编辑器只能产生纯文本段落块**，
因此导出的保真度**没有真实数据可验证**（标题、列表、代码块目前无处产生）。

建议路径：**先做 M1/M2 的块级格式菜单**（让块类型真的能被创建），
再做导出——那时导出才有东西可导、可验。

---

## 6. 明确不做的项与理由（备查）

| 项 | 理由 |
|---|---|
| 账户 / 登录 / 退出登录 | 本地优先架构下没有账户 |
| 共享 / 群聊 / 演示模式 | 无服务端协作能力 |
| 密码锁 | 用户 P1 明确说暂时不考虑 |
| 自定义工具栏 | 工具栏项少，可配置化的收益低于维护成本 |
| 打印 / PDF | 需要渲染层与字体嵌入决策；且与导出共享同一套渲染，应一起做 |
| 新建本地笔记本 | 本地优先下**全部**笔记本都是本地的，单独一个"本地"概念会让人困惑 |

---

## 7. 待用户确认的点

1. **阶段顺序**：M1 → M2 → M3 是否可以？还是先插一个 M2.5 做导出？
2. **菜单栏位置**：`MenuBar` 放在窗口顶部（跨三栏）——确认这是我们想要的形态？
3. **特色优先级**：§4 的五个特色，是否按 1→5 的顺序做？第一个（修订恢复）我建议最先做。
4. **"删除"的语义**：菜单里的"删除笔记"进回收站（现状）。是否需要在菜单里**同时**提供"彻底删除"？我倾向**不提供**——彻底删除只应在回收站里发生，防误触。
5. **快捷键冲突**：F10/F11/Ctrl+F11 与 Windows 系统/其它软件可能冲突，是否接受？若不接受，改用 Ctrl+1/2/3 切换三栏。
