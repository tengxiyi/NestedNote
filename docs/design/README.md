## 编号说明（重要，避免再次撞号）

技术方案 §48 的原始清单是"建议"，**缺少两项**（工程化与仓库结构、
编号归属未定），而实际实现时又新增了顶层文档。为保持"编号 = 阅读顺序"这一
唯一含义，现约定：

| 范围 | 归属 |
|---|---|
| `00`–`02` | 顶层文档：项目章程、开发计划、工程铁律 |
| `03` | **`docs/03-踩坑备忘.md`**（顶层，不是本目录）——过程性经验的集中记录 |
| `04`–`18` | 本目录的**模块设计**（见上表） |
| `19`– | 本目录的**功能规划**（"某个界面功能做哪些、不做哪些"） |

> `19` 为什么不插进 `08`–`18` 的空位：那些编号已在技术方案 §48 里
> 预留了**具体模块名**（Flutter 项目架构、编辑器、搜索……）。
> 占用其中一个会让"编号 ↔ 模块"的对应关系彻底乱掉。
>
> 规划类文档从 `19` 起独立编号，代价是编号顺序不再等于阅读顺序——
> 这个代价比"模块编号错位"小得多。

⚠️ **踩过的坑**：本项目一开始把三份设计文档写成了 `04`/`05`/`06`，
既与"`03` 是项目总体架构"的预留冲突，整体又比 §48 的规划低了一格。
趁引用还少时已统一修正。

**教训**：编号一旦被引用（CHANGELOG、别的设计文档、报告），改名成本会迅速上升。
因此**开新文档前先在此表登记编号**，不要直接照抄技术文档的示例清单——
那份清单是规划建议，不是最终编号。

## 规则（铁律 M1 / M2）

- **先设计后编码**：新模块或架构级功能开工前必须有设计文档；"边写边想"地实现架构级功能是禁止的。
- **决策进 ADR**：设计文档里做技术选型时，选型结论与其备选方案要落到 `docs/adr/`。
- **与代码同 PR 更新**：行为变了，设计文档必须在同一个 PR 里更新（铁律 M3）。
- **必须可执行**：涉及命令与配置的文档必须给出可复制的命令与预期输出。
- **诚实标注状态**：每份设计文档都要区分"已实现 / 未实现"，并写出未实现部分的计划阶段。
  把"打算这么做"写成"已经这样"是本项目最需要避免的文档缺陷。
